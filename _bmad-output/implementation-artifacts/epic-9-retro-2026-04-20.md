## Challenges

### 1. AC text repeatedly sloppy about `.` signed-print semantics

Several story ACs were written with expected outputs that ignored how `.` actually behaves. ANS Forth is unambiguous here: `.` prints **signed** 16-bit in the current `BASE`; `U.` prints unsigned. Specifically:

- 9.1 AC #7 originally expected `HEX #42 .` → `42 `. Correct: `2A ` (decimal 42 rendered in HEX).
- 9.2 AC #7 originally expected `$ffff .` → `65535 ` and `$aBcD .` → `43981 `. Correct: `-1 ` and `-21555 ` (signed-print). Tests corrected to use `U.` for the unsigned-16-bit intent.
- 9.6 AC #5 row 3 (`HEX FF . DECIMAL`) originally expected `255 ok`. `.` fires BEFORE `DECIMAL` takes effect — correct: `FF  ok`.
- 9.6 AC #5 row 8 (`65535 .`) originally expected `65535 ok`. Signed-print — correct: `-1  ok`.

**None were code bugs — all were spec-drafting errors caught during dev/review.** The pattern: AC drafters didn't mentally trace through signed-print × current-BASE × argument-order. ANS behaviour is standardized — there's no excuse for getting it wrong at the spec level.

### 2. Florid QA / audit prose

Story 9.6 leaned hard on "spirit gate" / "literal vs spirit reading" phrasing for the NFR1 drift outcome. Project-lead feedback: *"the test/qa language got a bit florid, y'all kept banging on about 'spirit gates' and whatnot. baffling."*

Audit prose should be plain diagnostic output. When a measured value misses a written gate and the miss is acceptable, say so directly: "measured 11.6%, gate was ≤1%, accepted because ~80 µs at 4 MHz is below the CP/M I/O timing floor." No need to dress it up as "the literal gate fails but the spirit is upheld". Saved as `feedback_plain_qa_language.md`.

### 3. NFR1 gate was written against a stale model

The written NFR1 "≤ 1% drift on unprefixed-path parse time" was based on 9.1's back-of-envelope "~50 T fast-fail" estimate, made when the dispatch chain had one arm. By 9.5 the chain had 6 arms + a dispatch-level flag reset — total fast-fail body grew to 214 T + 105 T threading = 319 T (≈4× the original estimate). The gate measurable-missed (11.6% actual), even though the absolute cost is user-invisible at CP/M clock speeds.

The 9.1 estimate wasn't wrong at the time it was made — the gate inherited from it just didn't get refreshed as the feature scope was fully revealed. For Epic 10+, rewrite the analogous gate as **"user-invisible at CP/M clock speeds"** (bounded, O(1)-in-token-length, below the I/O floor), not as a literal percentage drift number.

### 4. Binary-size predictions drifted on the duplication-heavy stories

9.2 (+237 actual vs +120–180 predicted) and 9.4 (+201 vs +150 cap) both missed their bands. Driver in both cases: code structurally-duplicated-then-consolidated. The prediction framework works well on clean additive work (9.1, 9.3, 9.5, 9.6 all within band or zero) but understates on stories that *temporarily* carry known duplication before a later consolidation.

Not a release blocker; just a calibration observation. The epic-total of +757 is defensible and justified per NFR4 (Phase-2 revision removed the net-negative gate).

### 5. Spec-number staleness and backwards-operand-order mishap

Two spec-documentation issues surfaced late:

- 9.1's Completion Notes "~50 T fast-fail overhead" quoted value was already 4× stale by 9.6 (see #3 above). Flagged in 9.6 Finding F2; refresh deferred.
- 9.5's story spec used *backwards* Zilog operand order in its CODE-block examples (`<value> # <reg> LD,` vs correct `<reg> <value> # LD,`). Caught by the dev agent at REPL-smoke time before committing tests. Per project memory `feedback_assembler_operand_order.md` — the convention is explicit, but the story spec author still got it wrong.

## Key Insights

1. **Scaffold-upfront design compounds.** 9.1 spent real spec-writing effort on a 6-arm dispatch table that only needed `#` on day one. That investment made 9.2, 9.3, 9.4 small, additive, and zero-restructure. The opposite pattern — grow the encoding organically, refactor when it hurts — would have cost rework at each story boundary. Worth the upfront cost every time (`feedback_design_upfront.md`).

2. **"Temporary duplication, consolidate at the right story" is a real pattern, not laziness.** The sign-in-body block was knowingly duplicated 4× across 9.1–9.3 because 9.4 was the pre-planned home for the refactor. 9.4 paid the debt off cleanly (−31 B net). Forcing premature abstraction in 9.2 would have locked in the wrong shape before the full requirement set was known. Trust the plan.

3. **FR9 ("no `BASE` mutation") forced per-base specialisation, which accidentally produced a performance win.** The constraint that prefix parsing must never temporarily mutate `BASE` meant the dev agent had to write `do_number_base10/16/2` rather than call the generic `do_number` with a BASE override. Those helpers hard-code the `*BASE` multiplier as 3–4 `ADD HL,HL`/`DE` ops, skipping the generic 16-iter shift-and-add. Result: prefixed path is 2.5× faster than unprefixed. **Lesson: strict constraints frequently produce better code than permissive ones.**

4. **ANS / Forth 2014 standards are unambiguous — spec-drafting errors are drafter errors, not "open to interpretation".** The `.` vs `U.` drift recurred across four stories. The standard says what the standard says; there's no excuse for AC authors missing it. For Epic 10+ AC drafting, add a quick trace-it-through check for any AC that names `.` / `U.` / `.R` / `U.R` / `D.` / `D.R`.

5. **Hardware smoke remains the gold standard.** The emulator passed 405 tests; the hardware then passed 12/12 smoke on real silicon. No divergence — but the hardware check is what earned the release-readiness sign-off, not the emulator count. Keep the discipline.

6. **"Adversarial" review genuinely earns its keep on audit-only stories too.** 9.6 was "just an audit" — dev made no functional edits — yet two authoritative review passes surfaced 2 HIGH + 4 MEDIUM + 3 LOW findings between them, including a wrong-NFR citation (`NFR13` where `NFR12` was meant). Exactly the class of error CCD-3 / NFR17 exist to catch. `feedback_adversarial_review.md` continues to hold.

7. **Strict constraints on prose format matter — florid audit language obscures facts.** Verdict tables should read as diagnostic output, not rhetorical argument. `feedback_plain_qa_language.md` saved.

## The Lazy-Load Assembler Decision (2026-04-20)

A major mid-epic event was the project lead's decision to drop the ASSEMBLER.FTH lazy-load capstone that Phase-2 was originally built around. Processed via `bmad-bmm-correct-course`; full reasoning captured in `sprint-change-proposal-2026-04-20.md` and now preserved as project memory `project_assembler_keep_assembly.md`.

**Three converging reasons:**

| # | Reason |
|---|---|
| i | The existing `src/assembler.asm` is elegant and heavily optimized — Epics 4–8 spent real effort tuning it. The original plan would have thrown that work away for a rewrite. |
| ii | `ASSEMBLER.FTH` would likely have been *bigger* than the current assembly version, and probably less elegant. |
| iii | The original motivation (boot-ROM qualification via kernel size reduction) was self-defeating. Base AntForth in ROM without an assembler means the user has to faff with secondary disk images for a usable Z80 Forth. **Nobody wants a Z80 Forth without an assembler.** |

**Trade-off accepted:** AntForth forfeits boot-ROM qualification to keep the product complete-out-of-the-box. Deliberate product decision, not retreat.

**Structural consequences:** PRD FR count 52 → 47; NFR count 23 → 21; Epic 12.7 / 13.5 / 13.6 deleted; Epic 12.8 → 12.7 and 13.7 → 13.5 renumbered. All done cleanly before any implementation work started on those stories.
