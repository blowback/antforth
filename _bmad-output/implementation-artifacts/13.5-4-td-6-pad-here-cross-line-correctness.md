## Story

As an antforth user writing interactive Forth at the REPL or in `INCLUDED` source where transient-region buffers must survive across one or more space-delimited parse steps (e.g., a multi-line probe that does `READ-FILE` to a transient address on line N and reads it back on line N+1; or any program relying on `/PAD ENVIRONMENT?`'s `( 84 -1 )` claim that a PAD region is available),
I want a `PAD` word that returns the address of a transient region whose contents survive the parsing of any one space-delimited name (per ANS Forth 1994 §6.2.2000 / §3.3.3.6), and a documented canonical guidance distinguishing PAD (single-line transient) from CREATE'd buffers (permanent across all operations) from HERE (volatile across every parse step),
So that idiomatic interactive use like `S" file" R/O OPEN-FILE THROW PAD 6 ROT READ-FILE THROW DROP CR PAD 6 TYPE` works as written across two REPL lines instead of silently emitting the next line's parsed-counted-string in place of the file content, and so the project's `/PAD ENVIRONMENT?` claim is structurally honoured by a real PAD surface.

This is the fifth story in Epic 13.5 (Phase-2 Cleanup Slate) — the process-recovery vehicle that gates `antforth 2.0`. It has zero new feature scope; the AC slate discharges the TD-6 debt named in the Epic 13 retro's Tag-Blocking Slate. The fix shape is **constrained but not pre-decided** at story-spec time — `epics.md:1818` enumerates three options (a) reserve a dedicated transient buffer separate from PAD and HERE that survives across REPL lines (data ~80..+128 bytes), (b) document the volatility and update kernel call sites to use stable buffers (zero binary delta, doc + tests only), (c) make PAD survive across one line while keeping HERE volatile (small data + small code). AC #2 commits the dev-pass to a single pick after the AC #1 catalogue completes, with criteria-driven justification and HALT discipline if no option fits cleanly.

## Severity Re-Statement (BINDING — context for every dev-pass decision)

Two correctness defects shareing one mental-model gap, both currently silent under regression tests, both reachable from any cross-line REPL use of "transient region" semantics:

| TD | Defect | Currently observable? | Current behaviour | Standard-required behaviour |
|----|--------|------------------------|-------------------|----------------------------|
| **TD-6 (a)** | `PAD` word does not exist | YES — trivially: `PAD` at the REPL throws -13 ("undefined word"); `/PAD ENVIRONMENT?` returns `( 84 -1 )` simultaneously claiming a 84-byte PAD region is available. The compliance claim diverges from the delivered surface | `src/system.asm:458..460` and `src/constants.asm:44` define `PAD_OFFSET = 84` and emit `( 84 -1 )` from `ENVIRONMENT?`. No `w_PAD` / `w_PAD_cf` exists in any of `src/*.asm`. `grep -rn "PAD\\b" src/` confirms no DEFCODE / DEFWORD for PAD | ANS Forth 1994 §6.2.2000 `PAD` ( -- c-addr ): "c-addr is the address of a transient region that can be used to hold data for intermediate processing." If `/PAD ENVIRONMENT?` returns `( 84 -1 )` (the antforth surface does), §3.2.6 implies PAD-the-word must be a real word that returns the start of a region of at least that size |
| **TD-6 (b)** | HERE-based "transient buffer" silently corrupts across REPL lines | YES — F-9 reproducer: line N stores `READ-FILE 6` output at HERE; line N+1's first space-delimited token (e.g., `S" SZ="`) writes its counted-string output at HERE+1, clobbering bytes 1..count of the line-N data. F-9 caught this on real CP/M / MicroBeast hardware as `\\x04type\\x1A` instead of file content. iz-cpm emulation has the same behaviour but no existing test exercised the cross-line HERE pattern, so it never surfaced under `make test-repl` | `src/strings.asm:67..150` — `WORD` writes a counted string at HERE+1..HERE+1+count, with count ≤ 31 (F_LENMASK). Any byte stored at HERE+1..HERE+32 is destroyed on the next parse step. The Story 13.5 F3 review-fix "use HERE not PAD" propagated this anti-affordance into Story 13.6's smoke-batch authoring, where it surfaced on hardware run 1 | The standard's transient-region semantics for PAD (§3.3.3.6) explicitly require survival across "the application's parsing of any one space-delimited name". HERE's contents have no such guarantee — HERE is the dictionary boundary, and the parser reasonably uses HERE+1.. as scratch. The fix is to surface PAD (or an equivalent stable transient region) AND to document the canonical guidance that HERE is wrong for cross-line buffers |

The fix shape is **dev-pass-picked** between three constrained options — see AC #2 — but the **scope is pinned**: closing TD-6(a) (the missing-PAD-word compliance gap) and TD-6(b) (the HERE-as-cross-line-buffer anti-affordance) is non-negotiable per S8 standing commitment. Either both close cleanly or HALT.

**Why the defects were silent in regression:** TD-6(a) is silent because no regression test invokes `PAD` directly (it would throw -13 if it did, which is also a valid "PAD-undefined" indirect probe — but no current test does). TD-6(b) is silent because no regression test exercises the cross-line HERE-buffer pattern — every existing `HERE` use in `Makefile` (35 occurrences) either reads HERE on the same line it stores (`HERE 100 FA @ READ-FILE DROP DROP` followed by same-line `FILE-POSITION`), or treats HERE as a dictionary-allotment cursor (`HERE WORDLIST DROP HERE SWAP -`), or uses HERE in the canonical `,`-and-`!` dictionary-emission idiom. None of them spans two REPL lines with HERE-stored data needing to survive.

**S8 reminder (codified Lesson 13-B per `feedback_no_preexisting_discharge.md`):** TD-6 may NOT be discharged with "accepted-with-rationale: pre-existing" or "smoke-batch authoring bug" — both Story 13.5's F3 disposition ("LOW (out-of-scope, documented)") and Story 13.6's F-9 disposition ("LOW (downgraded from HIGH-CANDIDATE) … NOT a kernel defect") were retroactively re-classified upward at the Epic 13 retro 2026-05-05 by project-lead direction. Either it lands cleanly here (option a) or the dev-pass HALTs and surfaces (option b per AC #12). No third option.

### Why HERE-stays-volatile is non-negotiable

A counterfactual fix shape — make HERE survive across REPL lines — is structurally not viable:

1. **HERE is the dictionary boundary.** Every word definition (`:`, `CREATE`, `VARIABLE`, `CONSTANT`, etc.) advances HERE. Making HERE survive across lines means every parse step would have to either (i) not write through HERE+1.. (impossible — `,` `C,` `WORD` etc. all do, by design), or (ii) save HERE before the write and restore it after — but then HERE wouldn't be the dictionary boundary anymore.
2. **WORD's HERE+1 staging is load-bearing for the outer interpreter.** `src/strings.asm:78..150` writes the parsed counted-string at HERE+1..HERE+1+count, then the outer interpreter at `src/outer_interpreter.asm` consumes that counted-string for FIND lookup. Moving WORD's staging elsewhere requires reshuffling the outer-interpreter contract — load-bearing, out-of-scope for a TD closure.
3. **The standard agrees.** ANS §3.3.3.6 says PAD survives single-parse; it does NOT say HERE survives single-parse. The volatility of HERE is allowed. The fix is to surface PAD as a separate, stable transient region — exactly what pick (c) does.

So the fix shape is "add a stable transient region word", not "change HERE's semantics". Picks (a) and (c) both add such a word; (b) acknowledges PAD-the-word stays missing and forces all cross-line use to CREATE'd buffers.

### Register-convention pick

```
w_PAD:
        DEFCODE "PAD", 0
w_PAD_cf:
        PUSH    BC                                ; save old TOS
        LD      L, (IY+UserArea.here)
        LD      H, (IY+UserArea.here+1)           ; HL = HERE
```
