## Successes

### 1. The Phase-4 prework gate is structurally clean

Every gating prerequisite that Epic 17+ story-writing blocks on is now resolved with a durable, source-of-truth artifact:

- F3 closed by a real hardware transcript, not an assumption.
- F1 closed by a vendor pick with explicit pass/pass/pass per-criterion justification and an integrated harness target.

No `TODO(P4-arch)` / `TODO(P4-resolve)` markers remain in the active surface. Stories 17.1 / 17.3 / 17.4 / 17.5 / 22.x have binding inputs, not negotiable ones.

### 2. Single-run hardware verification for 16.1

Story 16.1's hardware run produced a clean PASS on the first attempt — versus Story 15.5's three runs to land its 6 ACs. The probe was a single human-typed sequence (boot → run antforth → `BYE`/`^C` → check CCP prompt) per S12, not a batch of REPL probes that needed word-existence pre-flight or TIB-128 line-length lint. The deliverable was the transcript itself, not a probe; no probe-shape defects could surface because there was no probe.

This is the cost-effective shape for hardware-verification spikes: when the verdict is a single observable BIOS-level behaviour, hand-typed verification beats a probe batch. Calibration data point for future hardware-verification spikes.

### 3. `iz-cpm-banking` pick was clean (no SCP fork)

Story 16.3's AC2 named a fallback path: if zero candidates satisfied all three pinned criteria, the story was supposed to escalate to `/bmad-bmm-correct-course` rather than force a pick. The fallback wasn't needed — `iz-cpm-banking` (the `blowback/iz-cpm` fork at `1777a85`) satisfies (a)/(b)/(c) cleanly. The pick is also a same-upstream fork, so vendor-relationship risk is minimal.

This validates the "name the fallback in the AC" pattern from Stories 13.4.1 / 11.5.1.1 — the SCP/correct-course escape hatch is in the spec, so dev-pass doesn't have to invent one if the criteria don't fit reality. Cost is one bullet of AC text; benefit is structural deterministic-handling of the worst case.

## Challenges

### 1. Two planning-doc refresh commits between Phase-3 close and Epic 16 dev-pass introduced both surprises above

The drift / defect cluster — the deleted `epics.md` (commit `51bc6d6` — broke `check-doc-sync.sh`) and the inserted PD-P4-10 (commit `1775617` — bumped Story 16.4's numbering) — both originated in the same two-day window (2026-05-10) of between-epic planning-doc refresh commits.

The Phase-3 retro framed the between-epic gap as a "hitch-hiker landing zone" (D1 test 968 landed here cleanly). That framing was right for the test commit, but the planning-doc refresh commits in the same window need a separate framing: they're not hitch-hikers, they're spec-edit work that downstream stories then have to re-validate.

Both were caught (16.1 Task 1.4 surface; 16.4 dev-pass B.4 cross-walk). The B.4 + S8 conventions did their job. But it's worth naming the pattern: **between-epic gaps are mixed-traffic — direct-commit tests AND planning-doc edits — and the planning-doc edits create figure-drift work for the next epic's stories.**

### 2. `kernel_end:` future-edit reference is forward-only — Story 17.1's developer still has to verify

Story 16.1 AC5 captured a future-edit reference for Story 17.1 in its Dev Notes (`src/antforth.asm:290`; the `kernel_end:` declaration site; current 24,995-byte kernel sits roughly $0100..$6296). The reference is a "where to start" pointer, not a binding spec. Story 17.1's developer will re-verify the line number and the byte arithmetic at dev-pass time per B.3 / Lesson 13.5-F.

This is correct — the alternative (over-specifying the edit in 16.1) would inherit drift. Just noting it: the prework gate is not "Story 17.1 is half-done" — 17.1 starts from a verified-safe region but still has to make the layout decision (where `bank-table[]` base lives in $D400-$DBFF; how the descriptor-stub allocator carves the rest).

### 3. 16.3's first iron probe asserts via direct port I/O, not via `BANK!`

Story 16.3 AC6 said the first iron probe "confirms the banking-capable emulator can run a Forth script and assert MMU-port state via `SET-BANK`". `SET-BANK` doesn't exist yet (Epic 17 word). The probe was authored against port 0x72 directly (inline `CODE BANG-72 / FETCH-72` words from the Epic 4 assembler) — round-tripping a marker byte $36 through the slot-2 MMU port.

The probe PASSes under `iz-cpm-banking`, SKIPs cleanly under iz-cpm, and demonstrates that the harness end-to-end composition (iz-cpm-banking → make test-repl-banking → Forth → port I/O → readback) works. But it doesn't validate the eventual `BANK!` word's behaviour because `BANK!` doesn't exist yet.

This is fine — the AC's `SET-BANK` reference was forward-looking, and the actual probe demonstrates the load-bearing integration evidence. Story 17.2 (which ships `BANK@` / `BANK!` / `BANKS`) will be the first story that uses the harness against the actual surface it's meant to test.

### 4. Banner-block fork-β (already-banner-exists) for 16.2 turned a "create" task into an "edit" task

16.2's Task 1 found that a `> **⚠️ SUPERSEDED 2026-05-09.**` block already existed at `docs/antforth-banking-design.md:3` from commit `51bc6d6` (the same PRD-update commit that broke `check-doc-sync.sh`). The AC asked for the banner to be "inserted at the very top"; the dev-pass had to restructure the existing single-paragraph block into the enumerated `(a)/(b)` form rather than insert a fresh block.

This is a sibling pattern to Challenge 1 — between-epic planning-doc commits create surprise pre-state for downstream stories. Easy to handle in this case (fork-β rationale was captured; the restructure was a single hunk); but worth noting: a story whose AC says "create X" should also handle the case "X already exists (incidentally)" without a panic.

### 5. Story 16.4 surface was broader than the 5-AC spec suggested

Story 16.4's spec was 9 ACs that all reduced to "decide §9.X, document in architecture.md". The dev-pass touched four documents (architecture.md, prd.md, epics-phase4-..., docs/antforth-banking-redesign.md) with **20+ cross-reference updates** (lines :60, :150..154, :461, :483, :510..514, :607..614, :793, :844, :923, :979..985, :993, :1008, :1076, :1107, etc. in architecture.md alone — see 16.4 Completion Notes). The decision count was 5; the propagation count was 20+.

This is structurally fine — closing a redesign-doc § means *all* cross-document references to that § need updating. Just worth noting the ratio: a 5-decision story produced a 20+-cross-reference edit pass. The audit-and-propagate shape is intrinsic to "close binding architectural decisions" stories; future planning-doc-touching stories should expect similar fan-out.
