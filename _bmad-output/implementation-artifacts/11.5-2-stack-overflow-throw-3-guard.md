# Story 11.5.2: Stack-overflow `-3 THROW` guard

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Forth user,
I want data-stack growth past the parameter-stack limit to raise `-3 THROW` cleanly rather than corrupt whatever lives below the allocated stack region,
so that catastrophic stack-overflow becomes a recoverable error like every other migrated raise site (closes the Story 11.8 NFR6 documented gap).

## Acceptance Criteria

1. **Given** `THROW_STACK_OVERFLOW EQU -3` is reserved per `docs/throw-codes.md:74` (row `-3 | stack overflow | no | —`) and is currently absent from `src/constants.asm`,
   **when** the EQU is added,
   **then** it appears in `src/constants.asm` immediately above `THROW_STACK_UNDERFLOW EQU -4` (alphabetical-by-code), carries the `; ANS Forth 1994 §9.3.5` citation per CCD-3, and the `docs/throw-codes.md:74` row is updated from `no | —` to `done — Story 11.5.2 | <site>` (matching the §b table convention used for `-4` row 75).

2. **Given** the existing `check_underflow{,_2,_3,_4}` infrastructure in `src/system.asm:486-573` (each routine: `LD HL, (sp_base) / OR A / SBC HL, SP / branch on threshold / JP do_underflow_error`),
   **when** a symmetric `check_overflow` guard is authored,
   **then** it computes `HL = sp_base - SP_measured` (same setup as `check_underflow`) and raises `-3 THROW` via `JP do_overflow_error` (or equivalent) if `HL >= PS_SIZE` (= 256), accounting for the 2 bytes of CALL-return-address already on SP. The guard preserves BC (TOS), DE (IP), IX, IY, SP per the existing `check_underflow` contract; clobbers AF, HL.

3. **Given** the new `do_overflow_error` subroutine,
   **when** invoked from `check_overflow`,
   **then** it loads `BC = THROW_STACK_OVERFLOW` and `JP w_THROW_cf.kernel_entry` (kernel-internal entry pattern from Story 11.4), mirroring `do_underflow_error` at `src/system.asm:592-595` exactly. Inline citation `; -3 THROW: stack overflow per ANS Forth 1994 §9.3.5` lands in the comment header (CCD-3 / NFR17).

4. **Given** the dev agent must decide which call sites need the guard,
   **when** the analysis is performed at dev-pass start,
   **then** the dev agent produces an explicit "guard-site inventory" in Completion Notes Task 1 listing each site that pushes onto the data stack from a *depth-unaware* caller (analogous to the ~52 sites that today `CALL check_underflow{_,2,_3,_4}`). The inventory distinguishes:
   - **Inner-loop / hot-path sites** (e.g., `w_LIT_cf` push of literal, number-parser push from `INTERPRET`, `DUP` / `OVER` cell-pushes) where guard cycle cost matters.
   - **Cold-path sites** (e.g., compiler-time `,` `C,` `ALLOT`, banner string copies) where the cost is irrelevant.
   - **Sites already implicitly safe** (depth-decreasing or depth-neutral words: `DROP`, `+`, `=`) — these already shrink the stack and need no guard. Document the omission rationale per site to prevent later confusion.

5. **Given** the guard-site inventory from AC #4,
   **when** the dev agent decides between (a) wire `check_overflow` at every push-site individually, (b) instrument the inner-interpreter `NEXT` macro / `w_LIT_cf` once-per-thread-step, or (c) instrument the outer-interpreter / number-parser once-per-input-token,
   **then** the chosen approach is recorded in Completion Notes Task 2 with cycle-cost and ROM-cost rationale; option (a) is the safest (catches every push, never under-reports overflow); option (b) is cheaper but only catches LIT-driven pushes; option (c) is cheapest but only catches user-input growth (misses runaway colon-body LIT chains). The recommendation, absent contrary evidence, is **option (a) for hot-path push sites whose CALL-clobber tolerance matches `check_underflow`'s pattern, plus option (c) for the outer-interpreter / INTERPRET token push** (catches both the runaway-loop and runaway-input cases).

6. **Given** the guard fires before SP actually crosses the floor,
   **when** the threshold is computed,
   **then** the threshold accounts for: (a) the 2 bytes of CALL-return-address on SP at the moment `check_overflow` runs (same convention as `check_underflow`); (b) the 2 bytes the about-to-execute `PUSH BC` will consume; (c) the safety margin needed for `do_overflow_error`'s own CALL-chain into `w_THROW_cf.kernel_entry` and the THROW-uncaught path's diagnostic emission (which itself uses a few stack cells before the SP-restore happens). The exact threshold value (e.g., `HL >= PS_SIZE - 8` or similar) is dev-agent computed and justified in Completion Notes Task 3 with reference to the THROW path's worst-case SP usage between guard fire and SP-restore. **The guard MUST NOT raise THROW from a site where THROW itself cannot complete without re-tripping the guard.**

7. **Given** the THROW-uncaught path must succeed in unwinding even from the very condition that tripped the guard,

15. **Given** the adversarial-review discipline (`feedback_adversarial_review.md`),
    **when** Story 11.5.2's review runs,
    **then** **at least 1-2 HIGH/MEDIUM findings are expected**. Likely candidates the review must probe:
    - **(a) Threshold off-by-one / off-by-two** — the threshold computation (AC #6) involves three contributions (CALL-ret on SP, upcoming PUSH, THROW-path SP usage). Mis-budgeting any of these means the guard either trips early (false-positive overflow) or trips late (the actual overflow corrupts memory before the guard fires). Verify the threshold by *constructing* the worst-case THROW-uncaught-path SP trace and checking the guard's threshold leaves room for it.
    - **(b) Site-coverage completeness** — does the guard-site inventory miss a push site? A missing site silently re-introduces the same gap the story is supposed to close. The review must spot-check at least 5 push sites against the inventory (e.g., grep `PUSH BC` and confirm each appears in the inventory or is justified-omitted).
    - **(c) Re-entrancy / recursion under THROW** — if `do_overflow_error`'s path through `w_THROW_cf.kernel_entry` itself encounters a stack-tight condition, does the guard recurse? Compare to `do_underflow_error`'s comment (`src/system.asm:585-590`) which notes the underflow path neither reads nor writes SP-relative data until the downstream restore. The overflow path must satisfy the same property.
    - **(d) ABORT / ABORT" interaction** — Story 11.7 retargeted ABORT and ABORT" to `-1 THROW` and `-2 THROW`. ABORT" emits a string then THROWs; the string emission itself uses BDOS fn 9 (DE = string ptr). If the guard fires inside ABORT"'s string-emit path (not the path itself but a transitive caller in the failing program), does the THROW-string emission still complete? The audit must verify ABORT"'s post-string-emit SP state remains within the guard threshold.
    - **(e) DEPTH semantics post-overflow** — per `feedback_tos_in_register.md` (memory `project_tos_in_register.md`): DEPTH = (sp_base - SP)/2 counts SP cells only, not BC. If overflow trips with BC live (TOS-cell), the caught path's restored stack has DEPTH = pre-CATCH-DEPTH per Story 11.4.1 — but if BC is *not* live (e.g., overflow tripped during a depth-decreasing op's PUSH-then-pop cycle), the DEPTH could differ. Audit Section 6's expected DEPTH against this nuance.
    - **(f) Hardware-smoke gate** — the new test 779 is an iz-cpm REPL test; for Epic 11.5 close-out (Story 11.5.7) it must also pass on real MicroBeast hardware. Verify the test's overflow-trigger pattern doesn't itself depend on BDOS shadow-preservation (per Story 11.5.1.2 verdict, shadow is clobbered on fns 1 / 10 — but the overflow-trigger should be a tight inner loop that doesn't call BDOS at all until the THROW fires).

    Triage all findings; HIGH and MEDIUM block the gate; LOW may be accepted with rationale (mirror Stories 11.4-11.8 review-log discipline).

### Z80 / antforth conventions relevant to this story

Per `docs/register-conventions.md` and `_bmad-output/planning-artifacts/architecture.md`:

1. **TOS-in-register (BC = TOS).** The topmost data-stack value is held in BC; SP holds the SECOND-from-top. A push of a new value is `PUSH BC; LD BC, <new>` (BC's old value goes to the stack memory; BC is reloaded). This means the SP cell pressure happens at PUSH BC, which is precisely where the new guard belongs.
2. **Parameter stack grows DOWNWARD from `sp_base`.** `sp_base` is the empty-stack SP value (= TPA top, = BDOS base). The stack region runs from `sp_base - PS_SIZE` (= the floor, where the next push would underflow) to `sp_base` (= empty). PS_SIZE = 256 bytes = 128 cells.
3. **Return stack uses IX**, not SP. IX rstack is in a separate region below the data stack: `sp_base - PS_SIZE` to `sp_base - PS_SIZE - RS_SIZE`. Stack collision is "lazy invariant violation → THROW" per `architecture.md:768`. The new guard catches the data-stack side of this collision.
4. **DEPTH = (sp_base - SP) / 2.** Counts SP cells only, not BC. After `-3 THROW` is caught, the THROW caught path's `LD SP, HL / PUSH BC` (BC = -3 by then) restores DEPTH to pre-CATCH-DEPTH per Story 11.4.1.
5. **`check_underflow` family.** The 4 variants enforce DEPTH thresholds 1/2/3/4 (in cells). They use `LD HL, (sp_base) / OR A / SBC HL, SP` to compute `sp_base - SP_measured`, then branch on a hard-coded threshold (4 / 6 / 8 / 10 bytes — the +2 accounts for the CALL-ret-addr already on SP). The new `check_overflow` mirrors this exactly but with the threshold inverted (HL >= some-large-number ⇒ overflow).
6. **TOS-in-register & BC-may-be-phantom.** Per memory `project_tos_in_register.md`: BC=TOS may be phantom after ABORT; DEPTH = (sp_base-SP)/2 counts SP cells only, not BC; DEPTH=0 means BC invalid. After `-3 THROW`'s caught path restores via `PUSH BC`, BC is re-validated as TOS. Pre-fire, BC is whatever the failing word held; the guard preserves BC across its execution per AC #2 — this is critical because the THROW path's saved-BC slot (frame +2) was captured at CATCH entry, NOT at THROW fire, so BC at THROW fire is irrelevant to the caught-path stack restore.

### Story 11.4.1 i\*x preservation invariant (apply unchanged)

Per `architecture.md:301-314` (E11-D2 + post-D2 i\*x note): the THROW caught path restores BC from the CATCH frame's +2 slot (which was captured AT CATCH ENTRY, not at THROW fire), executes `LD SP, HL` (HL = saved-SP = SP_safe = SP after CATCH's POP BC), then `PUSH BC` to restore the i\*x's TOS-cell. Then BC is loaded with the THROW code (n) and NEXT runs. Net effect: data stack contains [i\*x's deepest, ..., i\*x's TOS, n] and BC = n.

For Story 11.5.2, this means: when `-3 THROW` fires inside a CATCH frame, the i\*x cells underneath that frame are preserved; the user sees `-3` on top with their pre-CATCH stack underneath. AC #9 Section 6.2 verifies this with the `1 2 3 ' TOV CATCH . . . .` pattern (expect `-3 3 2 1`).

### Threshold computation reference trace (AC #6, Task 3.4)

The new `check_overflow`'s threshold must leave room for the THROW path itself. The trace:

1. Caller does `CALL check_overflow` → pushes 2 ret bytes; SP_measured = SP_real - 2.
2. `check_overflow` runs: `LD HL, (sp_base) / OR A / SBC HL, SP` computes HL = sp_base - SP_measured = (bytes consumed including the 2 ret-addr bytes).
3. If HL >= threshold, JR/JP `.overflow` → `JP do_overflow_error` (no SP change — JP not CALL).
4. `do_overflow_error` runs: `LD BC, THROW_STACK_OVERFLOW / JP w_THROW_cf.kernel_entry` (no SP change).
5. `w_THROW_cf.kernel_entry` (per `src/exception.asm:267..` — review at dev-pass start) traces:
   - Read `CATCH-TOP`. If non-zero (caught path): O(active-INCLUDE-nesting) cleanup, then SP wholesale restored from CATCH frame +0; the SP-relative writes during the cleanup walk happen on IX (rstack), not SP — so SP isn't touched until the wholesale restore. **Caught path SP usage between guard fire and SP restore: 0 additional bytes.**
   - If zero (uncaught path): `.throw_uncaught` runs (`src/exception.asm:402-417`). Trace this path in detail. The diagnostic emission ("error -<code>: <desc>") uses BDOS fn 9 (DE = string ptr). BDOS fn 9 internally uses some stack — but it returns to `.throw_uncaught` BEFORE the wholesale `LD SP, (sp_base)` runs, so the BDOS-internal stack usage is reclaimed (BDOS pops what it pushed). The next instruction after BDOS-return is the diagnostic-format chain, which uses memory cells (`throw_saved_n` etc.), not SP. **Uncaught path SP usage between guard fire and SP restore: ~6-12 bytes (BDOS fn 9 entry + format-routine internals)** — verify by inspection.
6. Required margin: 2 (CALL ret-addr) + 2 (upcoming PUSH BC) + 12 (THROW-uncaught path worst-case) = **16 bytes** of safety margin. Threshold: `HL >= PS_SIZE - 16` = `HL >= 240` ⇒ overflow.

The dev agent verifies this trace at write-time (the THROW-uncaught path may have changed since story drafting; re-read `src/exception.asm:402-417` and trace SP precisely). The threshold value above is a story-drafting estimate; the exact value lands in the dev-pass.

**Site classification** (a/b/c per AC #4):

The 97 PUSH BC sites split roughly as:
- **(a) push-only-after-underflow-check** (paired pre-existing guards):
  ~15 sites — e.g., `w_OVER_cf` after `CALL check_underflow_2`,
  arithmetic ops after their underflow guards. Symmetric guard
  placement is obvious if guarded.
- **(b) depth-decreasing or depth-neutral net** (transient PUSH for
  register juggling, BDOS save/restore, EXX shuttling, or a

  `bdos_print_str:208`'s `PUSH BC` for save-across-`bdos_putchar`,

- **(c) depth-unaware net-growing pushes**: ~30+ candidate sites.

**Design choice (AC #5) — hybrid (b)+(c) with focused (b) variant**:

Guard at the **dispatch-level chokepoints** that catch the realistic
overflow scenarios with minimum site count and minimum cycle cost:

1. **Inner-interpreter dispatch guards** (option (b) restricted, NOT
   per-NEXT — only the 4 dispatch primitives that push as a side
   effect of running compiled colon bodies):
   - `w_LIT_cf` — push of inline literal (catches `BEGIN 1 AGAIN`)
   - `DOCON` — push of constant value (catches `BEGIN MYCONST AGAIN`)
   - `DOVAR` — push of variable body addr (catches `BEGIN MYVAR AGAIN`)
   - `DODOES` — push of DOES> body addr (catches DOES>-driven runaway)

2. **Outer-interpreter token-push guards** (option (c)):
   - `w_NUMBER_Q_cf` entry — catches EVALUATE/INCLUDE-driven overflow
     via long literal-number streams
   - `w_NUMBER_PREFIX_Q_cf` entry — same, with prefix recogniser
   - `w_ASM_RECOGNIZE_cf` entry — same, with assembler tag recogniser

3. **User-variable address-push helper** (option (a) at the single
   shared entry point — catches STATE / BASE / >IN / #TIB / CATCH-TOP
   all via one CALL):
   - `push_user_var` entry — guards all `JP push_user_var` callers
     in one place

**Total guard sites: 8.**

**Rationale for omitting per-primitive guards (DUP, OVER, ?DUP,
2DUP, 2OVER, TUCK, KEY, KEY?, DEPTH, HERE, R>, R@, SP@, RP@, BL,
SOURCE, etc.)**:

These are user-typed words executed at the inner-interpreter pace.
Realistic overflow analysis:
- **At REPL**: TIB_SIZE = 128 bytes; max ~25 words per input line
  (avg 5 chars/word + space). PS_SIZE/2 = 128 cells. A single
  REPL line of `DUP DUP DUP ...` (3-char DUP + space = 4 bytes,
  max 32 instances) cannot grow the stack past 32 cells from
  empty. Cannot overflow on a single line.
- **In compiled colon body**: A bomb like `: T DUP DUP DUP × 200 ;` IS
  theoretically possible but contrived. The user must manually
  author 200+ DUPs in a definition. Realistic accidental overflow
  goes through LIT (literals) or recursion (RECURSE), both caught.
- **In EVALUATE/INCLUDE**: long input strings COULD execute many
  DUPs sequentially, but the overflow vector that matters is the
  parsed-number push (covered by `w_NUMBER_Q_cf` entry guard).

The per-primitive bomb is a **known limitation** acceptable for this
story's scope. Documented in `docs/throw-codes.md:74` row's `<site>`
column. A future story may extend per-primitive coverage if the
adversarial review or hardware-smoke test surfaces a real-world
vector.

- Authored `check_overflow` at `src/system.asm:574` (immediately after

**Threshold derivation (AC #6, Task 3.4)**:

- Setup: caller does `CALL check_overflow` immediately before
  `PUSH BC`. At guard entry, SP = caller_SP - 2 (CALL ret addr).
  HL = sp_base - SP_measured = U_caller + 2.
- Constraint 1 (normal return): caller's `PUSH BC` after RET sets
  SP = caller_SP - 2 = SP_measured. Used after PUSH = HL_computed.
  Need: HL_computed <= PS_SIZE.
- Constraint 2 (overflow path): JP do_overflow_error → JP
  w_THROW_cf.kernel_entry → JR Z .throw_uncaught (uncaught path is
  the worst case; caught path's `LD SP, HL` from catch frame +0
  uses 0 additional SP). At .throw_uncaught entry: SP unchanged
  from check_overflow entry. Then sequence:
    - `LD (throw_saved_n), BC` — no SP change
    - `CALL bdos_print_str` — SP -= 2
      - inside loop: `PUSH HL` (-= 2), `PUSH BC` (-= 2),
        `CALL bdos_putchar` (-= 2)
        - `LD C, C_WRITE; CALL BDOS_ENTRY` (-= 2)
          - BDOS internals: caller-stack usage; CP/M 2.2 reference
            shows console writes use ~8-12 bytes. Conservative: 16.
      - deepest = HL_computed + 2 + 2 + 2 + 2 + 2 + 16 = HL + 26.
    - Subsequent CALL print_signed_dec_bc, CALL print_throw_description,
      CALL bdos_crlf, CALL asm_cleanup — each independently bounded
      by the same depth (none nest deeper than bdos_print_str's
      bdos_putchar→BDOS_ENTRY chain). Worst case ~HL + 28-30.
- Required margin: 32 bytes (covers measured ~30 with 8-byte
  alignment headroom).
- Threshold: trigger overflow when HL >= PS_SIZE - 32 = 224.
- Implementation: `CP PS_SIZE - 32` then `RET C` — sets CY when
  L < 224, returns. Falls through to `JP do_overflow_error` when
  L >= 224 (H is already known 0 from the prior `OR A; JR NZ`).

**THROW-caught path tolerance (AC #7, Task 3.5)**:

- Caught path: w_THROW_cf.kernel_entry → reads CATCH-TOP non-zero
  → `LD (throw_saved_n), BC` → `PUSH HL; POP IX` → reads frame
  fields (no SP changes; just IX-relative reads) → `LD BC, 8;
  ADD IX, BC` (IX += 8, no SP change) → reads saved-BC from IX-6
  (no SP) → `LD SP, HL` wholesale restore via catch frame +0
  (= SP_safe captured at CATCH entry, post-POP-BC, by definition
  outside the parameter-stack overflow zone).
- Caught path adds **2 bytes** of SP usage (`PUSH HL; POP IX` is
  paired) between guard fire and the wholesale restore. The 32-byte
  margin trivially covers it.

**MEDIUM finding** (acknowledged; accepted with rationale):
Per-primitive depth-growing sites (DUP, OVER, ?DUP, DEPTH, HERE,
KEY, KEY?, BL, R>, R@, SP@, RP@, SOURCE, 2DUP, 2OVER) are NOT
guarded. Rationale: these are user-typed words. At REPL,
TIB_SIZE = 128 bytes / max ~25 words per line, cannot grow stack
past 25 cells from empty. In compiled colon body, the bomb form
(`: T DUP DUP DUP × 200 ;`) requires deliberate authoring. All
*realistic-accident* overflow vectors go through LIT (literals),
DOCON (constants), DOVAR (variables), DODOES (DOES> words),
push_user_var (user variables), or NUMBER?-family (parsed numbers)
— all guarded. The deliberate-bomb form is acceptable as a known
limitation.

If a future story extends per-primitive coverage, the candidate
list above is the next-pass target.

**(c) Re-entrancy / recursion under THROW — VERIFIED safe.**

`do_overflow_error`'s body is identical-pattern to `do_underflow_
error` (both are 2-instruction LD BC, code / JP w_THROW_cf.kernel_
entry). The `kernel_entry` path:
- Loads `n` from BC (-3, non-zero, so n=0 short-circuit not taken).
- Reads CATCH-TOP. If non-zero (caught): LD (throw_saved_n), BC →
  IX/SP/CATCH-TOP/IP restore from frame; no SP-relative writes
  prior to the wholesale `LD SP, HL` restore. SP-may-be-tight
  property preserved.
- If zero (uncaught): `.throw_uncaught` chain. Same SP-tight
  property: no SP-relative writes prior to `LD SP, (sp_base)`.

The new guard's path neither re-enters check_overflow nor invokes
any guarded primitive. No recursion possible.

**(d) ABORT / ABORT" interaction — VERIFIED no risk.**

Story 11.7 retargeted ABORT to `-1 THROW` and ABORT" to a string-
emit then `-2 THROW`. ABORT"'s string-emit uses BDOS fn 9 (DE = string
ptr) via internal bdos_print_str — not via any of the 8 guarded
sites. The guard cannot fire inside ABORT"'s string-emit chain.

A pathological program that fills the stack then calls ABORT" would
trip the LIT guard during the fill (e.g., `BEGIN 1 0 UNTIL` style),
not inside ABORT"'s post-string THROW. The post-string THROW is
itself a JP into w_THROW_cf.kernel_entry — same SP-tight semantics
as do_overflow_error. No new risk from ABORT" interaction.

**(e) DEPTH semantics post-overflow — VERIFIED.**

Per memory `project_tos_in_register.md`: DEPTH counts SP cells only,
not BC. Section 6.3 test (`1 2 3 ' TOV CATCH . DEPTH .` → `-3 3
ok`) verifies the invariant empirically. Pre-CATCH DEPTH = 4
(3 i*x + xt). Post-CATCH stack = [phantom, 1, 2, 3, -3]; DEPTH
counts SP-cells = 4 (after the first `.` consumed BC=-3 from
register, SP-cells = 3). Matches Story 11.4.1 invariant.

**(f) Hardware-smoke gate — DOCUMENTED hardware-immune.**

Test 779's overflow trigger pattern (`: T779 BEGIN 1 0 UNTIL ;
T779`) executes entirely inside the inner interpreter (LIT, ?BRANCH)
without entering BDOS. BDOS is only invoked AFTER the THROW path's
wholesale SP reset (`.throw_uncaught` → bdos_print_str → BDOS fn 2);
any BDOS shadow-register clobber (per Story 11.5.1.2 verdict on
fns 1/10 — fn 2 is not in the verdict matrix but is conservatively
treated as suspect) cannot affect the data-stack overflow detection
or recovery.

For Epic 11.5 close-out (Story 11.5.7), test 779 is one of the
hardware-smoke targets. The trigger pattern is hardware-shadow-
clobber-immune by construction.
