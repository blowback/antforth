## Story

As an antforth user writing portable Forth code that needs to snapshot the current input position and rewind to it later within an `EVALUATE`d string (e.g., a self-modifying parser, a look-ahead helper that reads tokens then re-runs them, or any program built against the ANS Forth 1994 §6.2.2148 / §6.2.2125 contract),
I want user-facing `SAVE-INPUT` ( -- xn ... x1 n ) and `RESTORE-INPUT` ( xn ... x1 n -- flag ) words that work correctly when the current input source is `EVALUATE`-installed (SOURCE-ID = -1) — pushing a complete description of the current `(tib_addr, tib_len, >IN, SOURCE-ID)` quadruple onto the data stack on save, and restoring it on `RESTORE-INPUT` with `flag = 0` for matched-SOURCE-ID restores or `flag = -1` (true) for any source-changed / unrestorable case,
So that idiomatic ANS programs — `S" ... " EVALUATE` flows that capture state with `SAVE-INPUT`, mutate the parse cursor, then attempt `RESTORE-INPUT` to rewind — work as written, and so antforth's CORE-EXT wordset coverage gains the §6.2.2148 / §6.2.2125 entries that the retro Tag-Blocking Slate names as the sixth tag-blocker.

This is the sixth story in Epic 13.5 (Phase-2 Cleanup Slate) — the process-recovery vehicle that gates `antforth 2.0`. It has zero new feature scope; the AC slate discharges the TD-7 debt named in the Epic 13 retro's Tag-Blocking Slate. The fix shape is **constrained but not fully pre-decided** at story-spec time — `epics.md:1828` and the ANS spec together bracket the implementation, but the dev-pass picks the description-cell layout (uniform-quadruple vs source-discriminated) and the non-EVALUATE source policy after AC #1's investigation completes, with criteria-driven justification and HALT discipline if no option fits cleanly within the byte envelope.

### Why pick (a) (uniform-quadruple) is the default expected option (and the override criteria)

Pick (a) — uniform 4-cell description with `4` count on top — is the default expected pick for four reasons:

1. **The four USER-area source-spec slots are uniform across all SOURCE-ID classes.** `src/structures.asm:23-26` defines `tib_addr, tib_len, tib_in, source_id` — these four cells fully describe the current input source regardless of whether SOURCE-ID is 0 (keyboard), -1 (EVALUATE), or > 0 (INCLUDE-FILE). A uniform description shape captures all the state antforth's USER-area maintains. The EVALUATE arm (the binding scope) is closed by this shape; the keyboard and INCLUDE-FILE arms are also closed structurally (with the cross-REFILL caveat documented in AC #5 / compliance-doc).
2. **Byte cost is minimal and predictable.** ~50..+100 bytes for the two new words, well within the per-slate envelope from `epics.md:1828`. Pick (b) inflates by 70..80 bytes via the per-source dispatch.
3. **Matches gforth / SwiftForth convention.** Both reference Forths use uniform descriptions — different cell counts (gforth varies; SwiftForth uses 4 + count = 5) but uniform across source classes. A uniform-quadruple-with-count-on-top is the antforth-native shape of the same idiom.

### Register-convention pick

Both new word bodies (pick a) stay in primary-set context (no EXX). No state-dependent register pressure. Body shape sketches:

```
w_SAVE_INPUT:
        DEFCODE "SAVE-INPUT", 0
w_SAVE_INPUT_cf:
        PUSH    BC                                ; save old TOS
        ; Push tib_addr
        LD      L, (IY+UserArea.tib_addr)
        LD      H, (IY+UserArea.tib_addr+1)
        PUSH    HL
        ; Push tib_len
        LD      L, (IY+UserArea.tib_len)
        LD      H, (IY+UserArea.tib_len+1)
        PUSH    HL
        ; Push tib_in
        LD      L, (IY+UserArea.tib_in)
        LD      H, (IY+UserArea.tib_in+1)
        PUSH    HL
        ; Push source_id
        LD      L, (IY+UserArea.source_id)
        LD      H, (IY+UserArea.source_id+1)
        PUSH    HL
        ; New TOS = 4 (count)
        LD      BC, 4
        NEXT

w_RESTORE_INPUT:
        DEFCODE "RESTORE-INPUT", 0
w_RESTORE_INPUT_cf:
        ; BC = count cell from caller
        LD      A, C
        OR      A
        JR      NZ, .ri_check_count_high
        LD      A, B
        ; ... fall through to count check
.ri_check_count_high:
        ; if count != 4 → fail path: drop remaining + return -1
        LD      HL, 4
        SBC     HL, BC                            ; CY = 0 only if BC = 4 (with prior OR clearing CY)
        JR      NZ, .ri_count_mismatch
        ; Count = 4. Pop four cells in reverse SAVE-INPUT order:
        ; data stack TOS (under count) = source_id, then tib_in, then tib_len, then tib_addr.
        POP     HL
        ; Validate saved source_id == current source_id
        LD      A, (IY+UserArea.source_id)
        CP      L
        JR      NZ, .ri_src_mismatch
        LD      A, (IY+UserArea.source_id+1)
        CP      H
        JR      NZ, .ri_src_mismatch
        ; source_id matches; write back the four cells
        LD      (IY+UserArea.source_id), L
        LD      (IY+UserArea.source_id+1), H
        POP     HL
        LD      (IY+UserArea.tib_in), L
        LD      (IY+UserArea.tib_in+1), H
        POP     HL
        LD      (IY+UserArea.tib_len), L
        LD      (IY+UserArea.tib_len+1), H
        POP     HL
        LD      (IY+UserArea.tib_addr), L
        LD      (IY+UserArea.tib_addr+1), H
        LD      BC, 0                             ; flag = 0 (false / restored)
        NEXT
.ri_src_mismatch:
        ; saved source_id mismatches; drop remaining 3 cells
        POP     HL
        POP     HL
        POP     HL
        LD      BC, $FFFF                         ; flag = -1 (TRUE / cannot restore)
        NEXT
.ri_count_mismatch:
        ; Drop 'count' cells (BC of them) — for safety, drop up to a reasonable cap;
        ; if the user passed an absurd count, an underflow protection in the data
        ; stack drops what's there. The exact drop count is dev-pass-decided.
        ; ... (see Task 3.2 for final shape)
        LD      BC, $FFFF
        NEXT
```

Estimated cost (pick a): ~+50..+90 bytes total. The exact byte count is set by the assembler's instruction encoding; ±10 bytes within the +50..+100 envelope is normal. `docs/register-conventions.md` requires no edits — the BC-as-TOS convention is already documented; Story 13.5.5 follows it. The above sketch is illustrative — the dev-pass may improve the count-mismatch and src-mismatch fail paths' byte cost via subroutine sharing, and finalises the exact instruction sequence at Task 3 time.
