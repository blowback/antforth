## Story

As the antforth maintainer,
I want a thorough audit of every BDOS-call register-preservation assumption, every shadow-register / IX / IY / stack interaction with print paths, and a hardware reproduction of the 2026-04-27-observed crashes,
so that we produce a verdict (antforth defect / firmware bug / shared-fault) with reproducer for each path before approaching the MicroBeast firmware maintainer.

**This story is verdict-only — fix-stories spawn from the verdict; small in-pass fixes are not authorised.** The discipline is non-negotiable: if a one-line bug surfaces during the audit it goes into the verdict as a finding with reproducer, not into the source tree as a patch. The audit's "this is the defect" claim has to remain independently verifiable, and that means the source the audit reads is the same source a follow-up fix-story would patch — not a half-edited tree the dev pass already touched.

### Why -3085 implies BC-corruption pre-`print_throw_description`

The transcript shows `error -3085` after `THIS-DOES-NOT-EXIST`. The expected output is `error -13: undefined word` (per `src/exception.asm:585-587` `throw_desc_table` row for -13). The output shape `error -3085` (with no description) implies:

1. `print_signed_dec_bc` at `src/exception.asm:454` printed BC = -3085, not -13.
2. `print_throw_description` at `src/exception.asm:509` did the table walk on BC = -3085, found no match, returned silently (no `: <desc>` printed).

For (1) to happen, BC (or the cell `(throw_saved_n)` re-loaded into BC at `src/exception.asm:411,414`) was corrupted between the `-13 THROW` raise and `print_signed_dec_bc`'s consumption. The path is:

```
unknown-token raise → JP w_THROW_cf.kernel_entry (BC = -13)
  → check_underflow (no — kernel_entry skips it)
  → n=0 short-circuit (no — -13 ≠ 0)
  → CATCH-TOP read (= 0; no enclosing CATCH at REPL top level)
  → JR Z .throw_uncaught
.throw_uncaught:
  → LD (throw_saved_n), BC          ; throw_saved_n = -13
  → LD HL, str_throw_prefix
  → LD B, STR_THROW_PREFIX_LEN       ; B = 6
  → CALL bdos_print_str              ; ← BDOS call; clobbers per spec
  → LD BC, (throw_saved_n)           ; BC = ??? — this is the suspect read
  → CALL print_signed_dec_bc         ; prints whatever BC now holds
```

The suspect step is `LD BC, (throw_saved_n)` *after* a BDOS call. If MicroBeast BDOS overwrote memory at `throw_saved_n` (= a kernel-data DW at `src/exception.asm:673`), the re-load reads garbage. Hypothesis: BDOS function 2 (console output, called per-character via `bdos_putchar`) does not normally write to user memory, BUT a Bad-Sector chain (the BDOS error following incident #2) could imply the BDOS B: drive has corrupted state that's spilling into general memory. The hypothesis is testable: write a CP/M `.COM` that calls BDOS 2 in a tight loop while monitoring a known-address sentinel; if the sentinel changes, BDOS is writing where it shouldn't.

Alternative hypothesis: `throw_saved_n` is at a low-enough address (kernel data area, post-Story-11.7 binary 17,425 bytes from `0x0100`, so `throw_saved_n` sits near `0x4400`) that a BDOS file-system buffer overwrite into that region is plausible — *especially* if the immediately-prior session had a Bdos Err On B chain that left the BDOS in a recovering state. The transcript shows incident #2 followed several Bdos Err episodes (the user retyped after multiple drive errors). MicroBeast's BDOS may be unique in this regard.

Both hypotheses point at firmware bug or shared-fault, not antforth defect. But the audit must rule out the antforth-side alternatives first:
- Stack underflow during the THROW path corrupting `throw_saved_n` (no — `throw_saved_n` is in kernel data, not on the stack).
- Race with another concurrent operation (no — antforth is single-threaded; CP/M is single-threaded).
- Off-by-one bug in the description-table walk causing it to read past the end and return a phantom code (no — `print_throw_description` ends with `RET Z` on the terminator; -3085 is the input code, not the read code).

**Verdict (preliminary, pending audit):** likely (b) or (c) — firmware or shared-fault. Final verdict requires the audit's hardware reproduction.

### CP/M 2.2 BDOS register contract — what is and isn't guaranteed

Per Digital Research's *CP/M 2.2 Application Note* (Operating System Manual, 1979):

- **Entry contract:** C = function code; DE = parameter (or HL or stack, function-dependent); A clobbered.
- **Exit contract:** A = return value (or 0 on no-return-value); HL = 16-bit return where applicable; B = byte-pair return where applicable.
- **Clobber contract:** *"BDOS may destroy any of the registers BC, DE, HL."* In practice some implementations preserve more, but **the contract guarantees only A and the return value.**
- **Silence on:** IX, IY, AF (carry/flags), shadow registers (Z80 only — CP/M 2.2 was 8080-targeted, so the extension was not contemplated). antforth's reliance on IX (rstack), IY (user-area), and shadow-register preservation across BDOS is **not contractually guaranteed by CP/M 2.2**; the per-implementation behaviour determines correctness.

Real CP/M 2.2 implementations vary:
- Original 8080 BDOS preserves IX/IY (no Z80 instructions used); shadow set undefined.
- Z80-aware BDOS implementations (some MicroBeast / Sage / Cromemco builds) may use IX/IY internally and not save them.
- BDOS replacements (CP/M+ variants, ZSDOS, ZRDOS, Z80DOS, ZP/M) may have different conventions.

**Audit implication:** every IX/IY/shadow assumption in antforth across a BDOS call is a candidate finding. The MicroBeast-specific BDOS clobber-set must be empirically determined for the audit to assign verdicts. Task 2.4's hardware verification is the primary instrument.

#### Task 2 — Per-BDOS-site register-preservation audit

**CP/M 2.2 BDOS register contract** (Digital Research, *CP/M 2.2 Operating System Manual*, 1979, "Page Zero Use" + "BDOS Function Summary" + "Application Note: Registers"):

> Entry: register C contains the function code; register pair DE contains a parameter (function-dependent); other registers undefined to the BDOS.
> Exit: register A contains the function return value (also in L for 16-bit returns where applicable; in B for byte-pair returns).
> **The BDOS may destroy any register on return except A and the explicit return-pair where applicable.**

The contract is **silent on**: IX, IY, AF flag bits beyond the return-value indicator, and **all shadow registers** (BC', DE', HL', AF'). On 8080-target CP/M 2.2 the shadow set was outside the architectural model (no Z80 instructions), so the BDOS code itself could not have used them — but **MicroBeast's BDOS is Z80-aware**, and the maintainer is free to use the shadow set internally without violating the contract. **antforth's reliance on shadow-register preservation across BDOS is therefore unsupported by the spec.**

#### Task 3 — Story-11.4.1 implication: cell-by-cell trace of incident #1

**Verdict: RULED OUT as the *root* cause; CONTRIBUTING factor implicated.**

The `1 2 3 ' ABORT CATCH . . . .` reproducer is the exact Story 11.4.1 i\*x-preservation reproducer. Per `architecture.md:299-314`, post-Story-11.4.1 the data-stack invariant is:

```
After THROW caught path's LD SP, HL / PUSH BC / LD BC, n / NEXT:
  BC = -1                 (real TOS)
  [SP+0] = 3              (i*x's TOS-cell, restored from saved-BC)
  [SP+2] = 2              (i*x's second-from-top, NEVER written by xt's CALLs)
  [SP+4] = 1              (i*x's deepest, NEVER written by xt's CALLs)
```

These cells are correct **before any `.` runs**. The `. . . .` chain consumes them in order: `-1`, `3`, `2`, `1`. Session #2's retype confirms the i\*x cells are correct on hardware: `1 2 3 ' ABORT CATCH . . . .` → `-1 3 2 1  ok` works on retype every time.

**The crash on the *first* attempt is therefore not from i\*x corruption** — the correct values are present, and the retype completes fine without re-pushing. The crash sits in a subsequent `.` (probably the second or third) where the BDOS-clobber hypothesis explains everything: the colon `.` chain (S>D → D. → pictured-output → BDOS chars) accumulates BDOS calls; one of them clobbers IX or IY; the next primitive that reads IY-relative state (BASE, sp_base, CATCH-TOP, STATE) gets garbage and walks into bad memory.

**Cell-by-cell trace from session-#2 evidence:** the user did NOT produce a `.S`-instrumented trace of `1 2 3 ' ABORT CATCH` (Task 3.1's instrumented protocol). The evidence is structural: every retype of the same sequence completes cleanly, ruling out a deterministic i\*x bug. Story 11.4.1's redesign **holds** under the audit.

**Story 11.4.1 verdict: RULED OUT (with retype-evidence).** The Story-11.4.1 design is correct; the crash is downstream BDOS register clobber affecting `.`'s post-CATCH execution.

#### Task 4 — Verdict synthesis per incident

##### Incident #1 — `1 2 3 ' ABORT CATCH . . . .` soft-reboot mid-line

**Verdict: (c) shared-fault.**

**Antforth-side:**
- Multiple BDOS calls during `.`'s pictured-output chain rely on IX/IY preservation across BDOS. CP/M 2.2 BDOS contract does not guarantee IX/IY preservation. MicroBeast BDOS appears to clobber one or both non-deterministically.
- Mitigation cost: defensive `PUSH IX / PUSH IY` around every BDOS call site, or at the outer interpreter / NEXT boundary. ~30 sites × 4 bytes (PUSH+POP) = ~120 bytes ROM, plus ~70 T-states per site. The targeted fix is at the helper level (`bdos_putchar` / `bdos_crlf` / `bdos_print_str` / `bdos_print_q_crlf`), where 4 leaf functions absorb the cost instead of 30+ call sites — **~16 bytes total + 4 × 70 T-states** per site (one PUSH IX/PUSH IY pair per leaf entry, mirror POPs at exit).
- Risk: low. The leaves are cold paths during normal Forth execution (primitives spend most cycles in arithmetic/dictionary work, not in BDOS). The performance impact is bounded by the post-NFR3 budget (per-edit delta gate).

**Firmware-side:**
- MicroBeast BDOS clobbers IX / IY (and shadow registers — see incident #1 also implicates `.S`-class words via session #2's `.S` evidence). The CP/M 2.2 spec does not require preservation, so this is not a "bug" in the contract sense — but for a Z80-aware BDOS hosting a Z80 application that uses IX/IY/shadow for register-allocated state, preservation would be the courteous default.
- Reproducer for the maintainer: `bestialitty-20260427-155200.bin` lines 75-95 (the `5 4 3 2 1 .S` → `<5> 5 4 3 2 -512 ...soft-reboot` sequence). antforth's `.S` is small and self-contained; the BDOS-end behaviour can be probed directly.
- Antforth-side mitigation (defensive saves) closes the symptoms without firmware changes; the firmware-side note is "we'd appreciate IX/IY/shadow preservation in future BDOS revisions," not a release-blocker.

##### Incident #2 — `error -3085` + `Bdos Err On B: Bad Sector` chain

**Verdict: (c) shared-fault.**

**Antforth-side hypothesis (primary):** the `.throw_uncaught` chain at `src/exception.asm:402-432` executes:
```
LD (throw_saved_n), BC          ; throw_saved_n = -13 (the actual code)
LD HL, str_throw_prefix         
LD B, STR_THROW_PREFIX_LEN       
CALL bdos_print_str              ; ← BDOS call; many bdos_putchar inside
LD BC, (throw_saved_n)           ; BC = ??? — suspect re-load
CALL print_signed_dec_bc         ; prints whatever BC now holds
```

The path saves `n` to memory at `throw_saved_n` (`src/exception.asm:673` — a kernel-data `DW 0` immediately after the THROW description table), executes a BDOS call chain, then re-loads `n` from that memory cell. The corruption could be:

- (i) **Memory-side:** the BDOS overwrites memory at `throw_saved_n`'s address. The address sits in the kernel `.COM` data area (0x100 + offset; the `throw_saved_n` cell is well within the kernel's data range). Normal CP/M BDOS does not write outside its own working area + the user's DE-pointed buffer. **However**, the incident-#2 transcript shows a Bad-Sector chain *immediately following* the `error -3085` print — the BDOS was already in a degraded state from prior B: drive contention. A degraded BDOS could spill into adjacent memory.
- (ii) **Register-side:** `(throw_saved_n)` is intact; the issue is between `LD BC, (throw_saved_n)` and `CALL print_signed_dec_bc`. But there are no instructions between them. This is a non-issue — unless the LD itself reads a corrupted memory cell, which collapses to (i).
- (iii) **Cascade-side:** `n=-13` is correctly saved; `bdos_print_str` runs; the **HL/B register state** at the start of `bdos_print_str` is from the `LD HL, str_throw_prefix / LD B, STR_THROW_PREFIX_LEN` setup, but on re-entry to `.throw_uncaught` after BDOS, the post-print **A register** holds whatever the last BDOS call returned. If `LD BC, (throw_saved_n)` reads from a memory cell that itself was *cached* in a register and that register is in BC' shadow... no. The `LD BC, (throw_saved_n)` is a direct-memory read; it bypasses any register cache.

**The most defensible hypothesis is (i)** with a B: drive degradation precondition. The fix: stash `n` somewhere the BDOS *cannot* write — i.e., on the machine stack via `PUSH BC` instead of in `(throw_saved_n)`. The mechanical change is minor: replace the `LD (throw_saved_n), BC` save with `PUSH BC`, and the `LD BC, (throw_saved_n)` re-load with `POP BC`, restoring once after each consumer. **Same fix-story as Incident #1 closes this — a leaf-level register/memory-discipline pass on the print path.**

**Firmware-side:** the Bad-Sector chain following the `-3085` print is not antforth's symptom to fix; it's downstream BDOS state corruption. The MicroBeast maintainer would need to harden the B: drive recovery path. No reproducer required from antforth — the maintainer's existing B: drive diagnostics cover this.

##### Verdict converge: same fix-story closes both incidents

**Proposed Story 11.5.1.1 — `bdos-register-preservation-defensive-saves`** (subject to project-lead approval):
- **Scope:** harden every BDOS call site against IX/IY/shadow-register clobber and against memory-cell-save patterns that span a BDOS call.
- **Approach (cheapest, most-targeted):** add `PUSH IX / PUSH IY` at the entry of `bdos_putchar` / `bdos_crlf` / `bdos_print_str` / `bdos_print_q_crlf` (the 4 leaf helpers in `src/io.asm:188-225`); mirror `POP IY / POP IX` at exit. Net delta: ~16 bytes ROM (4 × 4 bytes per leaf for PUSH+POP pair). Closes ~30 IX/IY sites in one place.
- **Approach for shadow:** in `w_DOT_S_cf` (`src/formatting.asm:244-335`), restructure the EXX window — either (a) save IP to the rstack (`PUSH DE` at entry, `POP DE` at exit) instead of EXX, or (b) add explicit `PUSH BC / PUSH DE` around each BDOS call inside the EXX window. (a) is simpler and probably faster; (b) preserves the existing EXX-style.
- **Approach for `(throw_saved_n)` cell:** in `src/exception.asm:402-417`, replace the memory-cell save/restore with a machine-stack PUSH/POP — `PUSH BC` instead of `LD (throw_saved_n), BC`; `POP BC` (or `EX (SP), BC` if needed twice) instead of `LD BC, (throw_saved_n)`. Net delta: ~-2 bytes (DW removed; PUSH/POP replace LD-direct).
- **Tests required (in 11.5.1.1, not here):** REPL-piped `.S` regression at every depth (1..10); `1 2 3 ' ABORT CATCH . . . .` regression; uncaught-THROW description re-print regression. Hardware re-smoke as part of Story 11.5.7's CCD-4 close-out gate.
- **Risk:** low. Leaf-level edits; no semantic change; preserves all existing public contracts. The `.S` restructure is the main point of design judgment — choose (a) or (b) inside the spawned story.
- **Estimated binary delta:** **+10 to +20 bytes** (defensive saves) **−2 bytes** (`throw_saved_n` cell removed) = **~+10 bytes net**. Within the Epic-11.5 near-zero envelope per the sprint-change-proposal.

**Proposed Firmware-escalation reproducer (separate from 11.5.1.1):** a pure CP/M `.COM` (Z80 assembly source) ~50 bytes that:
