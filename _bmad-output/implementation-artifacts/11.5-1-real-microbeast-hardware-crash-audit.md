## Story

As the antforth maintainer,
I want a thorough audit of every BDOS-call register-preservation assumption, every shadow-register / IX / IY / stack interaction with print paths, and a hardware reproduction of the 2026-04-27-observed crashes,
so that we produce a verdict (antforth defect / firmware bug / shared-fault) with reproducer for each path before approaching the MicroBeast firmware maintainer.

**This story is verdict-only — fix-stories spawn from the verdict; small in-pass fixes are not authorised.** The discipline is non-negotiable: if a one-line bug surfaces during the audit it goes into the verdict as a finding with reproducer, not into the source tree as a patch. The audit's "this is the defect" claim has to remain independently verifiable, and that means the source the audit reads is the same source a follow-up fix-story would patch — not a half-edited tree the dev pass already touched.

### Why -3085 implies BC-corruption pre-`print_throw_description`

The transcript shows `error -3085` after `THIS-DOES-NOT-EXIST`. The expected output is `error -13: undefined word` (per `src/exception.asm:585-587` `throw_desc_table` row for -13). The output shape `error -3085` (with no description) implies:

1. `print_signed_dec_bc` at `src/exception.asm:454` printed BC = -3085, not -13.
2. `print_throw_description` at `src/exception.asm:509` did the table walk on BC = -3085, found no match, returned silently (no `: <desc>` printed).

For (1) to happen, BC (or the cell `(throw_saved_n)` re-loaded into BC at `src/exception.asm:411,414`) was corrupted between the `-13 THROW` raise and `print_signed_dec_bc`'s consumption. The path is:

```
unknown-token raise → JP w_THROW_cf.kernel_entry (BC = -13)
  → check_underflow (no — kernel_entry skips it)
  → n=0 short-circuit (no — -13 ≠ 0)
  → CATCH-TOP read (= 0; no enclosing CATCH at REPL top level)
  → JR Z .throw_uncaught
.throw_uncaught:
  → LD (throw_saved_n), BC          ; throw_saved_n = -13
  → LD HL, str_throw_prefix
  → LD B, STR_THROW_PREFIX_LEN       ; B = 6
  → CALL bdos_print_str              ; ← BDOS call; clobbers per spec
  → LD BC, (throw_saved_n)           ; BC = ??? — this is the suspect read
  → CALL print_signed_dec_bc         ; prints whatever BC now holds
```

The suspect step is `LD BC, (throw_saved_n)` *after* a BDOS call. If MicroBeast BDOS overwrote memory at `throw_saved_n` (= a kernel-data DW at `src/exception.asm:673`), the re-load reads garbage. Hypothesis: BDOS function 2 (console output, called per-character via `bdos_putchar`) does not normally write to user memory, BUT a Bad-Sector chain (the BDOS error following incident #2) could imply the BDOS B: drive has corrupted state that's spilling into general memory. The hypothesis is testable: write a CP/M `.COM` that calls BDOS 2 in a tight loop while monitoring a known-address sentinel; if the sentinel changes, BDOS is writing where it shouldn't.

Alternative hypothesis: `throw_saved_n` is at a low-enough address (kernel data area, post-Story-11.7 binary 17,425 bytes from `0x0100`, so `throw_saved_n` sits near `0x4400`) that a BDOS file-system buffer overwrite into that region is plausible — *especially* if the immediately-prior session had a Bdos Err On B chain that left the BDOS in a recovering state. The transcript shows incident #2 followed several Bdos Err episodes (the user retyped after multiple drive errors). MicroBeast's BDOS may be unique in this regard.

Both hypotheses point at firmware bug or shared-fault, not antforth defect. But the audit must rule out the antforth-side alternatives first:
- Stack underflow during the THROW path corrupting `throw_saved_n` (no — `throw_saved_n` is in kernel data, not on the stack).
- Race with another concurrent operation (no — antforth is single-threaded; CP/M is single-threaded).
- Off-by-one bug in the description-table walk causing it to read past the end and return a phantom code (no — `print_throw_description` ends with `RET Z` on the terminator; -3085 is the input code, not the read code).

**Verdict (preliminary, pending audit):** likely (b) or (c) — firmware or shared-fault. Final verdict requires the audit's hardware reproduction.

### CP/M 2.2 BDOS register contract — what is and isn't guaranteed

Per Digital Research's *CP/M 2.2 Application Note* (Operating System Manual, 1979):

- **Entry contract:** C = function code; DE = parameter (or HL or stack, function-dependent); A clobbered.
- **Exit contract:** A = return value (or 0 on no-return-value); HL = 16-bit return where applicable; B = byte-pair return where applicable.
- **Clobber contract:** *"BDOS may destroy any of the registers BC, DE, HL."* In practice some implementations preserve more, but **the contract guarantees only A and the return value.**
- **Silence on:** IX, IY, AF (carry/flags), shadow registers (Z80 only — CP/M 2.2 was 8080-targeted, so the extension was not contemplated). antforth's reliance on IX (rstack), IY (user-area), and shadow-register preservation across BDOS is **not contractually guaranteed by CP/M 2.2**; the per-implementation behaviour determines correctness.

Real CP/M 2.2 implementations vary:
- Original 8080 BDOS preserves IX/IY (no Z80 instructions used); shadow set undefined.
- Z80-aware BDOS implementations (some MicroBeast / Sage / Cromemco builds) may use IX/IY internally and not save them.
- BDOS replacements (CP/M+ variants, ZSDOS, ZRDOS, Z80DOS, ZP/M) may have different conventions.

**Audit implication:** every IX/IY/shadow assumption in antforth across a BDOS call is a candidate finding. The MicroBeast-specific BDOS clobber-set must be empirically determined for the audit to assign verdicts. Task 2.4's hardware verification is the primary instrument.
