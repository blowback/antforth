## Context — why this story exists, why now

Story 17.6 is the **Epic 17 close-out gate**. It carries three load-bearing pieces of work that the previous five binary-delta stories (17.1, 17.2, 17.3, 17.4, 17.5) explicitly deferred to this slot:

1. **Iron-spike validation of the Phase-4 banking layer end-to-end on real MicroBeast hardware.** Stories 17.1–17.5 brought up the `bank-table[]` allocator, the 9 user-facing `BANK*` words + `BANK-MAPPING-ON/OFF`, the CL-tail parser + boot configuration, the v3.0.1 banner with runtime `BANKS U.`, and the minimal `.BANKS` status table. None of them have actually exercised a **cross-bank call** on real hardware. The iron-spike — a hand-allocated code body in a banked page, dispatched via `BANK!` + `EXECUTE` against a known address, with `RET` back through the same-bank return convention — is the binding evidence that the banking layer is load-bearing for the descriptor-stub mechanism Epic 18 will build on top of it. Per the redesign §3 ("Cross-bank call mechanism") + §5.4 ("Per-bank state"), the iron-spike form has **no descriptor stub, no compiler integration, no sentinel-trampoline** — just the raw MMU-swap + direct dispatch. Failing the iron-spike means Epic 17 has shipped 10/12 user-facing wordset words that the user can observe at the REPL but cannot actually use to invoke banked code; that is a release blocker for the 3.0.1 tag.

2. **S11 user-visible version surface audit (NFR-P4-38).** Per `architecture.md:91` + `architecture.md:489..497` + `architecture.md:774..778` (Phase-4 file-touch surface) + `epics-phase4-epics-16-22.md:157` + the precedent established at Story 13.5.6 (v2.0.0 tag close-out), every Phase-4 antforth 3.x point-release tag MUST pass the user-visible version surface audit: banner / README / memory-file `description` fields all aligned to the new tag, plus `make check-doc-sync` clean. Story 17.6 OWNS the README + memory-file edits to align the remaining S11 surfaces with the 3.0.1 tag. Without this audit clean, the tag CANNOT apply per the NFR-P4-38 standing commitment.

### Design decisions

**D1 — Why include the iron-spike inside Epic 17's close-out story, instead of a standalone Story 17.7?**

- The iron-spike is BOTH the Epic-17 validation evidence (proves the banking layer is load-bearing before Epic 18 builds on it) AND a deliverable that ships under the 3.0.1 tag (validates the user-facing surface for cross-bank dispatch end-to-end). Splitting into a standalone story would mean either: (a) tagging 3.0.1 without iron-spike PASS evidence (defeats the validation gate; project lead would not accept), or (b) deferring 3.0.1 tag until a Story 17.7 closes (defers NFR-P4-21 epic-level-decoupling without value). Bundling iron-spike + close-out in Story 17.6 matches the epic-spec text (`epics-phase4-epics-16-22.md:584`) and the Story 13.5.6 / v2.0.0 close-out precedent (single close-out story carries verdict-table walk + tag application).

**D2 — Why bank 5 specifically for the iron-spike (vs bank 1, 7, 11, etc.)?**

- Bank 5 is a non-portal default user bank (per redesign §5.1 default page-allocation map: portal page is `0x22` → bank index 0; default user banks `0x35..0x3F` → bank indexes 1..11; bank 5 is `0x39` in the default mapping). Choice is arbitrary within the default 12-bank set; the epic-spec text at `epics-phase4-epics-16-22.md:594` chose bank 5 first; Story 17.6 preserves that choice for consistency with the epic-doc. Dev-pass discretion to use another bank index if there's a reason (e.g., 17.5.2 ends up using bank 5 for an unrelated probe and bank-5 state interaction becomes a concern); document choice in Dev Notes.

**D3 — Why is AC3 hardware PASS binding rather than a "best-effort" pass?**

- The whole Epic-17 banking foundation is hardware-motivated — the MMU is a real hardware port (`0x74` per Story 17.1); iz-cpm-banking is a software model of the MMU per Story 16.3. If the iron-spike PASSes on iz-cpm-banking but FAILs on real MicroBeast, the emulator's MMU model is wrong (or the antforth code has an emulator-specific assumption that real hardware doesn't honour); either case is a release blocker for 3.0.1. Per `feedback_no_accept_disposition_for_bugs.md` (STRONG rule), hardware-vs-emulator divergence is a BUG and dispatches to project-lead with a fix proposal — NOT an "accept-with-rationale" disposition.

**D4 — Why is the iron-spike "hand-built" instead of "use bank-aware `:` from Epic 19"?**

- Bank-aware `:` (Epic 19) requires the descriptor-stub mechanism (Epic 18) which requires the iron-spike validation (Story 17.6). Circular dependency if iron-spike depends on stubs. Hand-built form breaks the cycle: it's the most primitive cross-bank call shape possible (manual byte-stores + raw EXECUTE + RET), validating ONLY the banking layer (MMU swap + bank-table swap) without any of the dispatch infrastructure layers above it. After Epic 18 + Epic 19 ship, the iron-spike probe becomes informational-only (per AC4 source comment) — the user-facing cross-bank call surface is bank-aware `:` + transparent compile-time dispatch.

**D5 — Why does S11 audit (AC5) include the memory-file `description` field?**
