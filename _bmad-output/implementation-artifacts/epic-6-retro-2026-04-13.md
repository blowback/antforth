## Challenges

### 1. Estimation Accuracy (Systematic Bias in Both Directions)

Estimates were off by 2-4x in both directions:
- **Mechanical substitution stories overdelivered** (6.1-6.3): Z80 variable-length instruction encoding means IX/IY-prefixed instructions are 3-4 bytes, not the 2 bytes assumed in napkin math. Story 6.3 estimated 75 bytes and delivered 302 — a 4x overshoot.
- **Design-heavy stories underdelivered** (6.6, 6.7): The 6.6 recognizer body was ~2x larger than pseudocode suggested (DE save/restore, scratch variables, full comparison loop with UPPER). Story 6.6 estimated 136 and delivered 86.

**Root cause:** Estimates counted assumed instruction sizes rather than actual opcode byte counts from the Z80 reference.

### 2. rpop_bc Follow-Up Fell Through

Story 6.2's code review identified 14 unconverted rpop_bc inline sites (~61 bytes savings). This was tracked as a follow-up for story 6.7, but 6.7's scope was sign-negation dedup and tail-calls. The rpop_bc optimization never landed. Bytes left on the table.

### 3. Register-Contract Violations (Still the Dominant Bug Class)

Story 6.6's recognizer used DE as scratch for name comparison, corrupting the threaded IP. Caught during development (not in review this time). Same class of bug seen in Epics 4 and 5. Accepted as inherent to Z80 assembly — the review process catches every instance.

## Key Insights

1. **Mechanical substitution at scale is a proven methodology** — Create subroutine, grep for all inline sites, replace one-by-one, build-test after each batch. Repeatable, safe, and consistently overdelivers on estimates.
2. **Estimation needs real opcode byte counts** — Z80 variable-length encoding makes napkin math unreliable. Count actual bytes from the instruction set reference, especially for IX/IY-prefixed instructions.
3. **Shadow registers (EXX/EX AF,AF') are completely unused** — The Z80 shadow register set is sitting pristine in the codebase. A single EXX instruction (1 byte) can replace multiple PUSH/POP pairs or memory spill slots. The 6.6 recognizer is the prime candidate — its bulkiest code is saving/restoring DE to memory. Survey-then-fix investigation could yield significant further savings.
4. **Adversarial reviews remain essential** — Every story had findings. The review process is the primary defence against register-contract violations and missed optimization opportunities.
5. **Refactoring epics can dramatically overdeliver** — When the codebase has genuine mechanical repetition, extraction and dedup yield compounding returns. 48% over target is strong evidence.

## Significant Discovery: Shadow Register Opportunity

During the retrospective discussion, the project lead identified that the Z80 shadow register set (EXX, EX AF,AF') is completely unused in the AntForth codebase. Key observations:

- **EXX** (1 byte) swaps BC/DE/HL with BC'/DE'/HL' — can replace multi-register save/restore sequences
- **CP/M 2.2 BDOS does not use shadow registers** — they are pristine
- **No interrupt handlers** in AntForth — no contention for shadows
- **Prime candidate:** Story 6.6 recognizer (124 bytes), where the bulkiest code is saving/restoring DE to a memory scratch variable
- **Broader opportunity:** Any CODE word currently using `CALL rpush_de / CALL rpush_bc` at entry (12 bytes) could potentially use `EXX` (1 byte) instead
- **Convention needed:** EXX must be a leaf-level technique — no calling subroutines that also EXX

**Recommended approach:** Survey-then-fix (the pattern validated in Epic 5). Audit all CODE words for EXX opportunities, produce a survey doc, then implement from findings.

This discovery does NOT require updating any existing epic plans — no Epic 7 is defined yet. It should inform future planning.
