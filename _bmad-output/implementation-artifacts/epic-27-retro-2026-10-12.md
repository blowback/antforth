## Lead's verdict

- **Good:** we implemented some sorely-missed common words, and discovered and fixed some
  latent bugs along the way.
- **Bad:** available code space shrank, speed dropped 10–15%, and we're now limited to two
  tasks, which almost renders multitasking pointless. It's starting to feel bloated.

## What went well

- **Byte estimates were exact.** 27.1–27.4 matched to the byte; 27.6/27.7 within 1–4 B of
  their drafting estimates. Itemised per-word budgets work; the overrun was scope, not
  estimation.
- **Every story found a real defect outside its scope, and none was waved through.** `ROT`
  depth gap (27.1); the one-operand underflow gap, which became 27.6 (27.2); batnball's
  firmware tick source at `0xff04`, found only on hardware (27.2); the `>NUMBER` ud1 cell
  swap, latent since it was written because every test used `0 0` (27.6); the `WORD`/`PAD`
  spill past `$C000` (27.7).
- **27.7 diagnosed before fixing.** The "FIND bug" was physical-page aliasing caused by the
  probes' own repeated `$22 +BANK`, not a FIND defect. The trace stopped a FIND patch that
  would have fixed nothing, and found the one real defect (transient-buffer spill).
- **Structural fixes replaced repeated workarounds:** every bank-driving probe now runs
  under `timeout` with an rc-124 FAIL branch; the 12 multitasker-family targets are now
  `test-repl` prerequisites.

## What was hard

1. **Probe targets outside `test-repl` went unrun.** Kernel growth broke
   `-multitasker-bank` and `-mailbox` over 27.1–27.4 without anyone noticing, and 27.7's
   +36 B review fix broke `-multitasker-bank` again. Fixed in 27.5.
2. **Renaming probes around a known bug.** 27.3 (`_by` → `_wx/_wy/_wz`) and 27.4 (`B0` →
   `F0`) renamed probes to dodge the bank-lookup bug while it stayed open. 27.7 restored the
   original names.
3. **The underflow checks cost more than expected.** One `check_underflow` is 94 T-states
   (`NEXT` is 38 T); the journal had said ~50. `DUP` went from 49 T to 143 T (~2.9×).
   27.6 measured only the interpreter (+20.9% per typed token) and `INCLUDE`
   (+9.7–14.3%). **Compiled-code cost was never measured** and is likely worse in tight
   loops built from checked primitives. Check sites: 72 at v3.2.1, 150 at v3.3.0.
4. **Task room is nearly gone.** Fixed RAM below `$8000` now holds exactly two named TCBs
   (546 B each) with 25 B spare; a third `TASK` raises `-8`. Any kernel story over ~25 B
   breaks `TRAFFIC.FTH` and the two-TCB probes. Journal entry `docs/dev_journal.md:28` stays
   OPEN.

## Key insights

- Growth that was individually justified (safety checks, bug fixes) added up to a kernel
  that is bigger, slower and can barely multitask. The envelope was crossed twice with
  "accepted" each time; nothing stopped the epic to re-plan against the overall cost.
- The underflow checks are the one large cost that is a design choice rather than a
  requirement (ANS 94 treats underflow as an ambiguous condition). They are also the main
  speed cost.

## Underflow strategy options (for AI-27-3)

Recorded so the decision after AI-27-2 starts from the same analysis.

| | Bytes back | Compiled speed | Interpreter speed | Error at faulting word | Tasks protected |
|---|---|---|---|---|---|
| **A** keep per-primitive checks | 0 | slow | slow | yes | yes |
| **B** kernel threads call `w_X_cf + 3` (skip the 3-byte `CALL`) | 0 | slow | fast | yes | yes |
| **C** one depth check per word in `INTERPRET`, drop primitive checks | ~250–450 | fast | fast | no (late) | no |
| **D** cheaper helper (per-task precomputed limit, ~60 T?) | 0 | ~⅓ better | ~⅓ better | yes | yes |
| **E** build flag `SAFE=1/0` assembles checks in or out | all (fast build) | fast build | fast build | safe build | safe build |

- **B** is free and safe because the kernel thread itself produces every cell it consumes;
  it needs a build-time assert that each `+3` target really starts with the 3-byte `CALL`.
  It combines with A or E.
- **C** loses the FR-P7-14 goal, gives background tasks no check (they never pass through
  `INTERPRET`), and brings back the test-643 class of damage: `SP_GUARD` is only 8 B, so a
  looping over-pop walks past it and later pushes land over the BDOS entry.
- **E** is the only option that recovers bytes while keeping a checked build; costs a second
  test configuration and per-build task-room figures.
- Facilitator's lean (not a decision): B now, then A vs E on AI-27-2's numbers; avoid C.
