## Story

As the antforth maintainer,
I want a pure-CP/M `.COM` reproducer that probes each antforth-relevant BDOS function (1, 2, 6, 9, 10, 11) with sentinel values in every general-purpose register and shadow-register pair and reports per-register PRESERVED / CLOBBERED on the MicroBeast BDOS,
so that we obtain measured (not hypothesised) per-function clobber data for both an antforth-side decision (does Story 11.5.1.1 defensive-saves need to land?) and a firmware-side escalation packet for MicroBeast firmware maintainer Andy.

**This story is the firmware-escalation reproducer spec'd in Story 11.5.1 Task 4 §"Firmware-escalation reproducer" and approved by the project lead 2026-04-27 (Story 11.5.1 Task 5, decision #3).** Story 11.5.1.1 (`bdos-register-preservation-defensive-saves`) is held in contingent status — it spawns only if this story's reproducer is inconclusive.

**Scope is empirical, not diagnostic.** The reproducer reports facts (per-register before-vs-after across each BDOS function); it does not theorise about *why* MicroBeast BDOS clobbers what it clobbers. Verdict synthesis (escalate / spawn 11.5.1.1 / both) is a deliverable of this story; firmware-side root-cause analysis is Andy's domain.

## Acceptance Criteria

1. **Given** Story 11.5.1's audit verdict (c) shared-fault for both 2026-04-27 hardware-crash incidents, the project-lead approval 2026-04-27 (Story 11.5.1 Task 5, decision #3), and the spawned-row `11.5-1-2-firmware-bdos-register-preservation-reproducer: backlog` in `sprint-status.yaml`, **when** this story's reproducer artefact is authored, **then** the artefact is a self-contained CP/M 2.2 `.COM` (8080-or-Z80 instructions, no antforth dependencies — does not load, does not link against, and does not reference any symbol from `src/*.asm`) that runs from the CP/M command line via `BDOS-PRB` (or similar 8.3-conformant name) on either iz-cpm or real MicroBeast hardware. Source lives at a new path outside `src/` (recommended: `tools/bdos_probe/bdos_probe.asm`) and builds with the existing sjasmplus toolchain via a new `Makefile` target. **No edits to `src/*.asm`, `tests/*.fth`, or `docs/*.md` are authorised by this story** (mirrors Story 11.5.1's "no antforth-source edits" discipline; the reproducer is a new tool, not an antforth modification). Edits to `Makefile` are authorised solely to add the `firmware-repro` (or equivalent) target — no other Makefile changes.

2. **Given** the antforth-relevant BDOS function set (1 = `C_READ` blocking input; 2 = `C_WRITE` single-char output; 6 = `C_RAWIO` direct console I/O; 9 = `C_WRITESTR` `$`-terminated string output; 10 = `C_READSTR` line-buffered input; 11 = `C_STATUS` console-status non-blocking) per `src/constants.asm:9-14` plus the two CP/M-standard functions antforth does not currently use (6 and 9 — included because the firmware maintainer's investigation may want symmetric data), **when** the reproducer probes each of the six functions in turn, **then** each probe loads canonical sentinel values into BC, DE, HL, IX, IY, AF (A and F separately), BC', DE', HL', and AF' (A' and F'); invokes the BDOS function with the minimum necessary parameter setup for that function (e.g., function 2 needs `E` = char; function 9 needs `DE` = string-pointer); on return immediately snapshots all main and shadow registers to a fixed memory area before any subsequent code; and reports the snapshotted values against the sentinels.

3. **Given** the sentinel values, **when** authored, **then** the canonical sentinels are exactly:
    - **Main:** `BC = 0x1234`, `DE = 0x5678`, `HL = 0x9ABC`, `IX = 0xCAFE`, `IY = 0xBABE`, `A = 0xAA`, `F = 0x00` (all flags clear) — note: F's behaviour across BDOS is informational only, since the BDOS contract explicitly returns A as a result; F-clobber is expected.
    - **Shadow:** `BC' = 0xDEAD`, `DE' = 0xC0DE`, `HL' = 0xF00D`, `A' = 0x55`, `F' = 0xFF` (all flags set; complement of main).
    - **Rationale:** values chosen to be (a) easily eyeball-distinguishable from common stack/buffer noise (`0x0000`, `0xFFFF`, ASCII), (b) different per register so a clobber that overwrites with another register's value is visible (e.g. if BDOS clobbers BC' to 0xCAFE, the report shows the IX-shaped value, not just "clobbered"), (c) avoiding any bit-pattern that resembles a valid CP/M function code or a TPA-relative address. Functions 9 and 10 require the parameter slot (DE for function 9; DE for function 10) to point at a real buffer for the call to succeed without overwriting unrelated memory; the test runner saves the sentinel `DE = 0x5678` to a separate memory cell before each function-9/10 setup, and reports DE-divergence relative to the *parameter address used*, not relative to `0x5678`.

4. **Given** the per-function sentinel-and-snapshot protocol, **when** the reproducer runs, **then** for each BDOS function tested it prints exactly one result line in the form:

    ```
    Fn NN: BC=hhhh DE=hhhh HL=hhhh IX=hhhh IY=hhhh A=hh F=hh BC'=hhhh DE'=hhhh HL'=hhhh A'=hh F'=hh
    ```

    where `NN` is the function number (decimal, 2 digits) and each `hhhh`/`hh` is the post-call hex value of that register. The report is raw values, not P/C labels — the human reader compares against the sentinels printed in the leading "Sentinels:" line. Emitting raw hex is deliberate per `feedback_plain_qa_language.md`: state the *measured value*, let the gate (sentinel match) and the conclusion (PRESERVED / CLOBBERED) be derived by the reader. The leading line is exactly:

    ```
    Sentinels: BC=1234 DE=5678 HL=9ABC IX=CAFE IY=BABE A=AA F=00 BC'=DEAD DE'=C0DE HL'=F00D A'=55 F'=FF
    ```

5. **Given** functions 1 (`C_READ`) and 10 (`C_READSTR`) block until the user supplies input, **when** the reproducer reaches each, **then** it prints a single-line user-prompt (e.g. `"Press Enter for fn 01: "`) before invoking the function so the test operator knows a key/line is expected. The blocking-input prompt is the only conversational text in the reproducer; everything else is the "Sentinels:" line, the per-function result lines, and the trailing "Done" sentinel. **The reproducer must complete in ≤ 30 seconds of operator interaction** (six functions × ≤ 5 seconds each), so verdict capture is feasible inside a single transcript-recording session on real hardware.

6. **Given** the reproducer is authored and the dev agent has access to iz-cpm, **when** a self-test is run via `make firmware-repro-test` (or equivalent target that pipes the `.COM` through iz-cpm with canned blocking-input lines), **then** the iz-cpm pass yields *all-PRESERVED* across all six functions (iz-cpm's BDOS implementation is well-known not to clobber IX/IY/shadow). This is the **negative-control gate** for the reproducer: a clobber on iz-cpm would mean the reproducer itself is buggy, not that iz-cpm's BDOS is buggy. Self-test must record the iz-cpm output verbatim in the story's Completion Notes "Self-test (iz-cpm)" subsection. **If iz-cpm shows any clobber, the reproducer is rejected and re-authored — no hardware run until the negative-control passes.**

7. **Given** the negative-control gate passes, **when** the reproducer is transferred to real MicroBeast (per the established 2026-04-20 / 04-25 / 04-27 transfer mechanism — disk image build + write to MicroBeast media + the project-lead-half session), **then** project lead Ant runs the `.COM` on real MicroBeast with a transcript-capture session active. The captured transcript is saved to `~/Downloads/bestialitty-bdos-probe-YYYYMMDD-HHMMSS.bin` and referenced verbatim in the story's "Hardware run" Completion Notes subsection. **Two independent runs in separate CP/M sessions** are required (mirror Story 11.5.1 AC #8(d): "every reproducer must run twice on hardware, in independent sessions, with the same outcome"); divergent results across the two runs are themselves a finding (probabilistic clobber).

8. **Given** the hardware run results, **when** synthesised, **then** the story's "Verdict" Completion Notes subsection produces a **per-function × per-register matrix** — six rows (functions) × eleven columns (BC, DE, HL, IX, IY, A, F, BC', DE', HL', A'; F' is informational and folded into A's row) — with cells `P` (preserved across both runs), `C` (clobbered across both runs), `?` (divergent across runs — flagged for re-run), or `n/a` (function-9 / function-10 DE column). The matrix is the load-bearing deliverable; it directly determines whether Story 11.5.1.1 (defensive-saves) needs to spawn:
    - **All `P`** (no clobber on any function/register) → the audit's hypothesis is REFUTED. Stories 11.5.1.1 and the Andy escalation are both dropped. Story 11.5.1's verdict is amended (the audit hypothesis was wrong; the crash class is something else — re-audit required).
    - **Any `C` on a function/register that antforth uses (functions 1, 2, 10, 11; registers IX, IY, BC', DE', HL', A')** → firmware bug CONFIRMED for the affected (function, register) pair. The Andy-escalation packet (per AC #9) is prepared. Story 11.5.1.1 (defensive-saves) decision: spawned only if Andy declines to fix or the fix timeline conflicts with Epic 11.5 close-out (Story 11.5.7).
    - **`C` on functions 6 / 9 only** (functions antforth doesn't use) → Andy-escalation cover-note flag for firmware courtesy; antforth-side mitigation NOT required; Story 11.5.1.1 stays dormant.
    - **`?` on any cell** → re-run on hardware before the verdict closes; do not synthesise a verdict on probabilistic data.

9. **Given** the verdict matrix shows confirmed firmware clobber on antforth-relevant (function, register) pairs, **when** the escalation packet is composed, **then** it includes (delivered as a single email-or-Slack-ready Markdown block in the story's "Escalation packet" Completion Notes subsection): (a) cover paragraph stating the observed behaviour in plain language; (b) the per-function/register matrix from AC #8; (c) a link/attachment reference to the `.COM` artefact (built path); (d) the matching Z80 assembly source (link or inline); (e) the two captured hardware transcripts (paths); (f) the CP/M 2.2 BDOS contract citation (the MicroBeast BDOS is not violating the contract per the spec's silence on IX/IY/shadow — the cover paragraph says so explicitly to avoid framing this as a "bug" the maintainer is obligated to fix); (g) the antforth use-case (kernel-level Forth running on MicroBeast hosts a register-allocated runtime that benefits from BDOS preserving IX/IY/shadow; the spec is silent on these so antforth's reliance is technically un-contracted, but maintainer-provided preservation would close the field crash without antforth-side defensive saves); (h) explicit *non-demand* framing — Ant is asking, not requiring, since antforth has a fallback (Story 11.5.1.1 defensive saves). The packet is composed; project lead Ant chooses whether and when to send it.

10. **Given** the verdict matrix shows inconclusive results (any `?` cells unresolved by re-runs) or shows no firmware clobber on antforth-relevant pairs (so Andy escalation has no leverage), **when** the dev pass closes, **then** the story's "Sequencing decision" Completion Notes subsection records: (a) outcome of the firmware probe; (b) project-lead decision on whether to spawn Story 11.5.1.1 (`bdos-register-preservation-defensive-saves`); (c) if 11.5.1.1 is approved, the row is added to `sprint-status.yaml` as `11.5-1-1-bdos-register-preservation-defensive-saves: backlog` immediately above the existing 11.5-1-2 row (chronological insertion preserves audit parentage); (d) if 11.5.1.1 is dropped, the rationale is recorded in `project_hardware_crash_audit.md` (memory updated to reflect the field outcome and the closure-of-the-audit-hypothesis).

11. **Given** the adversarial-review discipline (`feedback_adversarial_review.md`), **when** Story 11.5.1.2's review runs, **then** **at least 1-2 HIGH/MEDIUM findings are expected**. Likely candidates the review must probe:
    - **(a)** Reproducer correctness — does the snapshot routine itself preserve every register before the snapshot is committed to memory? A single `LD A, ...` between BDOS-return and snapshot commits would corrupt the very value being measured. Self-test on iz-cpm should catch this, but the review must verify the order of operations is "BDOS RET → save AF first via PUSH AF → save other regs" with no intervening modifications.
    - **(b)** Sentinel-collision — does any sentinel value happen to match a value the BDOS would *legitimately* set on return? E.g. function 11 returns A=0x00 or 0xFF; if A's sentinel were 0xFF the function-11 row would mis-report A=PRESERVED. Audit each sentinel against each function's documented return semantics.
    - **(c)** Function-9 string-pointer leak — function 9 needs `DE` = pointer-to-`$`-terminated-string. The pointer's value will replace the DE sentinel pre-call; the post-call DE value is "function 9's clobber relative to the pointer," not "function 9's clobber relative to 0x5678." The result line for function 9 must clearly indicate "DE column n/a-during-call."
    - **(d)** Function-10 same-shape — function 10 needs `DE` = pointer-to-line-buffer. Same caveat as (c).
    - **(e)** Iz-cpm vs. MicroBeast tooling parity — does iz-cpm faithfully implement CP/M 2.2 BDOS (no Z80-extension behaviour iz-cpm "modernises")? If iz-cpm's BDOS is itself opinionated about IX/IY preservation, the negative-control gate weakens. Quick check: iz-cpm source is openly available; verify it implements function 2 et al as direct CALLs that don't touch IX/IY explicitly.
    - **(f)** Hardware-run reproducibility — AC #7's two-runs requirement is the same as Story 11.5.1 AC #8(d); single-run results don't gate-pass.
    - **(g)** Escalation-packet tone — per AC #9(h), framing is non-demanding; the review must verify no language reads as "MicroBeast BDOS is broken" — the spec says it isn't.
    - **(h)** Memory update completeness — `project_hardware_crash_audit.md` must reflect the field outcome at story close-out; if the memory still reads "audit complete; firmware reproducer next" after this story flips to `review`, that's a finding.

    Triage all findings; HIGH and MEDIUM block the gate; LOW may be accepted with rationale (mirror Stories 11.4-11.8 review-log discipline).

12. **Given** Story 11.5.1's verdict-only discipline does *not* propagate to this story (Story 11.5.1.2 IS a fix-story — it produces the firmware-escalation artefact; it is itself an authorised dev-pass), **when** small in-pass refinements to the reproducer are warranted (extra sentinel patterns, additional function probes beyond the six, polished output formatting), **then** they are landed inside this story — no spawning further sub-stories.   - [x] 2.2 Authored `load_sentinels:` subroutine. Implementation order chosen for clarity: shadow set first (EXX → load BC'/DE'/HL' → EXX), then shadow AF' via `LD HL, 0x55FF / PUSH HL / EX AF, AF' / POP AF / EX AF, AF'`, then main IX/IY/BC/DE, then main AF via `LD HL, 0xAA00 / PUSH HL / POP AF`, then final `LD HL, SENT_HL` to reload main HL (used as scratch for AF). Last instruction before `RET` is `LD HL, SENT_HL` which doesn't modify A or F. Verified by inspection AND by iz-cpm self-test (sentinel-loaded values appear in fn-2 result line for IX/IY/BC'/DE'/HL'/A'/F').
  - [x] 2.3 Author `snapshot_regs:` subroutine: invoked immediately after BDOS returns. **Order is critical** — the snapshot must save every register before any instruction can modify it. The required instruction order:
    1. `PUSH AF`        ; save flags (and A) FIRST — most volatile, modified by any arithmetic
    2. `LD (snap_bc), BC`
    3. `LD (snap_de), DE`
    4. `LD (snap_hl), HL`
    5. `LD (snap_ix), IX` (uses ED-prefix LD HL,(nn) form via DD/FD prefix)
    6. `LD (snap_iy), IY`
    7. `EXX`
    8. `LD (snap_bc2), BC` (these are now BC')
    9. `LD (snap_de2), DE`
    10. `LD (snap_hl2), HL`
    11. `EXX`            ; restore main
    12. `EX AF, AF'`
    13. `LD (snap_af2), HL`  -- nope; need a different approach for AF'
    Actually for AF / AF' the only way to save flags-byte is `PUSH AF / POP HL → LD (snap_af), HL`. So:
    1. `PUSH AF` → AF on stack
    2. `LD (snap_bc), BC; LD (snap_de), DE; LD (snap_hl), HL; LD (snap_ix), IX; LD (snap_iy), IY`
    3. `EX AF, AF'` then `PUSH AF` → AF' on stack
    4. `EXX` then `LD (snap_bc2), BC; LD (snap_de2), DE; LD (snap_hl2), HL; EXX`
    5. `POP HL → LD (snap_af2), HL`
    6. `EX AF, AF'` (restore main AF)
    7. `POP HL → LD (snap_af), HL`
    8. `RET`

    Implemented as discrete `DW 0` cells (one per register pair) rather than a `DS 24` block + offsets, for clarity and easier inspection in listings. 21 bytes total: `current_fn` (1) + 10 × `DW 0` (20). Layout per source: `current_fn`, `snap_bc`, `snap_de`, `snap_hl`, `snap_ix`, `snap_iy`, `snap_af`, `snap_bc2`, `snap_de2`, `snap_hl2`, `snap_af2`.
  - [x] 2.4 Snapshot self-clobber audit: every save uses `LD (nn), rr` (no register modification), `PUSH AF` (no register modification), `EX AF, AF'` (controlled swap, balanced by second `EX AF, AF'`), `EXX` (controlled swap, balanced by second `EXX`), `POP HL` (modifies HL but only AFTER `snap_hl` has been committed). No ALU / arithmetic / `LD A, ...` / flag-affecting op runs between routine entry and the final commit. **Verified** by iz-cpm self-test: IX/IY/BC'/DE'/HL'/A'/F' all read back as their loaded sentinels across all six probe rows.

Fixed by bracketing the inner call with `PUSH HL / POP HL`. Negative-control gate then passed cleanly. **This is exactly the kind of bug AC #11(a) primed the review to look for.**

### Z80 register-set primer for the reproducer's design

Per `docs/register-conventions.md` §1 the AntForth kernel uses BC/DE/HL/IX/IY in specific roles, and the shadow set (BC'/DE'/HL') is reachable only through `EXX`. The reproducer can use the registers freely (it has no Forth threading model to honour) — the only constraints are:

1. **CP/M `.COM` ABI:** entry at `0x0100` with SP = top-of-TPA; BC = TPA byte count from the loader; DE = command-tail buffer length; A,F undefined. The reproducer overwrites all of these in `load_sentinels` before any BDOS call.
2. **`EX AF, AF'` is the only way to reach AF'.** Saving `AF'` post-BDOS goes via `EX AF, AF' → PUSH AF → POP HL → LD (snap), HL → EX AF, AF'`. The two `EX AF, AF'` calls cancel — main AF unchanged net.
3. **`EXX` is unconditional and pairwise.** Two `EXX`es swap-and-swap-back. The snapshot routine uses `EXX → save shadow → EXX` so the main set is restored after.
4. **`PUSH IX` / `POP IX` cost 2 bytes / 17 T-states each** (DD prefix + PUSH/POP). The reproducer uses `LD (nn), IX` instead (4 bytes / 20 T-states), which leaves SP undisturbed — important since SP is unrelated to the BDOS contract and shouldn't be hammered.

### CP/M 2.2 BDOS function reference (only the six relevant)

Per Digital Research's *CP/M 2.2 Operating System Manual* (1979):

| Fn | Name | Entry | Exit |
|---|---|---|---|
| 1 | `C_READ` | C=1 | A = char read (echoed); blocks until char available |
| 2 | `C_WRITE` | C=2; E = char | (no return value; A undefined) |
| 6 | `C_RAWIO` | C=6; E = 0xFF (poll-input) or E ≠ 0xFF (raw output of E) | A = 0 (no char) or A = char (input mode); A undefined (output mode) |
| 9 | `C_WRITESTR` | C=9; DE = string ptr ($-terminated) | (no return; A undefined) |
| 10 | `C_READSTR` | C=10; DE = buffer ptr (DE[0]=max, DE[1]=actual on return, DE[2..] chars) | (no return value via register; buffer modified) |
| 11 | `C_STATUS` | C=11 | A = 0 (no char ready) or 0xFF (char ready) |

**Contractual clobbers** (Application Note: Registers): "BDOS may destroy any of the registers BC, DE, HL." Silent on IX, IY, AF (beyond return-value), and shadow registers. The reproducer measures the silence empirically.

**Functions and their parameter usage in the reproducer:**
- Functions 2, 11 — non-blocking, register-only setup. Pure PRESERVE/CLOBBER measurement.
- Functions 6 (E=0xFF non-blocking poll), 9 (DE-pointer to string) — DE replaced by pointer for fn 9; otherwise pure measurement.
- Functions 1, 10 — blocking; require operator input. A is contractually returned in fn 1 (A-clobber expected); DE is buffer-pointer in fn 10 (DE-replaced expected).

### Why six functions and not the full 0..40 range

Per Story 11.5.1 Task 5 decision #3: "BDOS functions 1, 2, 6, 9, 10, 11" — the project-lead's pick. Functions 0 (terminate) is unnecessary (the reproducer terminates via fn 0 anyway; if fn 0 clobbered registers, the program wouldn't return cleanly to CP/M, which is its own diagnostic). Functions 12+ (FCB-based file ops) are out of scope for the print-path crash class — they have their own register usage (DE = FCB pointer) and would warrant a separate audit if Epic 13 later surfaces FS-side crashes.

The minimum viable set for resolving the audit verdict is functions 2, 10, 11 (the antforth-used ones besides BYE's fn 0). Adding 1, 6, 9 gives Andy a richer dataset at zero additional development cost.

### Sentinel collision audit (AC #11(b))

Each sentinel is checked against each function's documented return semantics:

| Function | Documented A-on-return | Documented HL-on-return | Sentinel collision? |
|---|---|---|---|
| 1 | char read (ASCII 0x20-0x7E typical) | undefined | A=0xAA — outside ASCII; safe. (AA is a non-ASCII byte.) |
| 2 | undefined | undefined | None. |
| 6 | 0x00 or input char | undefined | A=0xAA — outside likely return. (Input chars are 0x20-0x7E typically; 0xAA is implausible.) |
| 9 | undefined | undefined | None. |
| 10 | undefined (buffer modified) | undefined | None. |
| 11 | 0x00 or 0xFF | undefined | A=0xAA — distinct from both. Safe. |

Other registers: BC, DE, HL, IX, IY, BC', DE', HL' have no documented return values, so any sentinel that's not commonly stack/buffer noise is safe. The chosen sentinels avoid `0x0000`, `0xFFFF`, and ASCII patterns. Cleared.
