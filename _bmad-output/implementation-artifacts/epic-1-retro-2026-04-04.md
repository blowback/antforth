## Challenges

### 1. Monolithic Test Thread (Structural)

The single test thread in `antforth.asm` grew from "ABCDE" (5 chars, Story 1.2) to 54+ characters across all stories. It's sequential — a failure early in the thread prevents all subsequent tests from running. Difficult to isolate which primitive failed without counting output characters.

**Resolution:** Will be modularised into per-module sections as part of Epic 2 Story 2.1. Long-term solution is Forth-based test scripts once the REPL is available (Story 2.2).

### 2. Test Coverage Incomplete on First Pass (Process — Recurring)

Stories 1.3, 1.4, and 1.5 all had test threads added during code review:
- Story 1.3: 10 missing test threads (PICK, ROLL, DEPTH, COMMA, ALLOT, etc.)
- Story 1.4: 10 FALSE-case and edge-case tests added
- Story 1.5: Multi-char TYPE test and negative SPACES test added

Test completeness was treated as a review catch rather than a first-class deliverable.

### 3. KEY/KEY? Manual Test Did Not Test Code Under Test (Critical — Process Failure)

The manual test program (`test_key.asm`) called BDOS routines directly instead of exercising the actual Forth primitives (`w_KEY`, `w_KEYQ`) through the threading model. This meant KEY and KEY? had **zero verification** of their actual implementation — the register save/restore, stack effects, and TOS convention were all untested.

**Root cause:** KEY/KEY? were originally classified as "can't automate" which became "won't test". When a manual test was later requested, the goal shifted from "verify our Forth primitives" to "verify the concept works". The resulting test proved CP/M BDOS works, not that our code works.

**Resolution:** Ant pushed back, the test was rewritten to exercise the actual Forth implementations through threaded code, and it now passes. However, the fix required project lead intervention — the process didn't catch it.

---

## Key Insights

1. **"Can't automate" means "needs manual test" — never "won't test"**
2. **Tests must exercise actual Forth implementations through the threading model** — no shortcuts bypassing the inner interpreter, no raw BDOS calls pretending to test Forth words
3. **Test completeness must be a first-class deliverable** — not something code review catches as a recurring theme
4. **Quality trajectory was strongly positive** — tooling issues and register contract violations dropped to zero by mid-epic, showing the team learns fast when patterns are established
