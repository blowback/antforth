## Story

As an antforth user invoking `."` in interpret mode (at the REPL, at the top level of an `INCLUDED` source file, or inside an `EVALUATE`d string outside a colon definition),
I want the data-stack TOS to remain unchanged across the call (as ANS §6.2.0190 `( -- )` requires),
So that idiomatic interactive use like `42 ." answer = " .` prints `answer = 42 ` instead of `answer = ` followed by garbage from the C register having been overwritten with the remaining TIB byte-count, and so that the project's TOS-in-register convention (`docs/register-conventions.md`: BC = TOS) is honoured by every IMMEDIATE word the user can directly invoke.

This is the fourth story in Epic 13.5 (Phase-2 Cleanup Slate) — the process-recovery vehicle that gates `antforth 2.0`. It has zero new feature scope; the AC slate discharges the TD-5 debt named in the Epic 13 retro's Tag-Blocking Slate. The fix shape was pre-scoped at Story 13.5 finding F2 (PUSH BC / POP BC envelope mirroring the compile-mode tail of the same word and the interpret-mode tail of `S"`); this story lands that shape, adds the missing interpret-mode regression probes, and updates the compliance documentation to record TD-5 closure.

## Severity Re-Statement (BINDING — context for every dev-pass decision)

One correctness defect, currently silent under compile-mode tests, reachable from any interpret-mode `."` invocation:

| TD | Defect | Currently observable? | Current behaviour | Standard-required behaviour |
|----|--------|------------------------|-------------------|----------------------------|
| **TD-5** | Interpret-mode `."` clobbers BC (TOS-in-register) | YES — trivially, via `42 ." x" .` at the REPL printing a wrong number after `x`; but no current `make test-repl` probe exercises interpret-mode `."` so the defect has been silent across every regression run | The interpret-mode tail at `src/strings.asm:834..900` writes the remaining-TIB byte-count into C at line 859 (`LD C, A`), clamps to 255 at line 864 (`LD C, 255`), and decrements C at line 873 (`DEC C`) on each loop iteration. The original BC (= TOS at function entry per `docs/register-conventions.md`) is never saved/restored across this work. Net effect: BC on return = 0 (loop-exhaust path) or 0 (terminator-found path with no stash) — the user's TOS is destroyed | ANS §6.2.0190 `."` ( -- ) — net stack effect must be empty, which (under the antforth TOS-in-BC convention) implies BC must be unchanged across the call. The compile-mode tail of the same word at `src/strings.asm:817/828` already honours this via `PUSH BC / POP BC` around `compile_string`; the interpret-mode tail must do the same |

The fix is **structural** — wrap the interpret-mode work in a `PUSH BC / POP BC` envelope mirroring the compile-mode tail of the same word and the interpret-mode tail of `S"`. The fix is byte-cheap (estimated +2..+10 code bytes), single-site, and zero data delta.

**Why the defect was silent in regression:** all existing `."` probes in `Makefile` (REPL tests 69, 75, plus several inside the file-access and pictured-numeric harnesses) define `."` inside a colon definition (`: HI ." Hello World" ; HI`). At compile time, `."` is IMMEDIATE and emits `(S")` + inline string + `TYPE` into the dictionary. At run-time of the compiled colon body, `(S")` pushes c-addr, sets BC = u, and `TYPE` consumes both — the net stack effect of the compiled-out form is empty AND the runtime path correctly threads BC through the stack. The bug only surfaces when `."` itself runs in interpret state (state == 0), and no current regression probe exercises that path. Closing TD-5 also closes the regression-coverage gap.

**S8 reminder (codified Lesson 13-B per `feedback_no_preexisting_discharge.md`):** TD-5 may NOT be discharged with "accepted-with-rationale: pre-existing" — it was named a tag-blocker at the Epic 13 retro 2026-05-05 by project-lead direction, explicitly citing this exact finding as the prototypical example of the anti-pattern. Either it lands cleanly here (option a) or the dev-pass HALTs and surfaces (option b per AC #11). No third option.

### Why the fix is `PUSH BC / POP BC`, not `EXX`

The spec at `epics.md:1808` allows either: "code +10..+30 bytes — a typical EXX-or-PUSH/POP wrap of the BC-clobbering inner code". The dev-pass picks `PUSH BC / POP BC` for three reasons:

1. **Local symmetry.** The compile-mode tail of the SAME word at `:817/828` uses `PUSH BC / POP BC`. The interpret-mode tail of the COMPANION word `S"` at `:715` uses `PUSH BC` (with a matching POP-equivalent via the new-TOS replacement at `:789..790`). Mirroring the existing pattern minimises the cognitive load on future readers — they see one idiom across all three sites.
2. **Byte-cheaper.** `PUSH BC / POP BC` is 2 bytes (`0xC5 0xC1`); `EXX / EXX` is 2 bytes (`0xD9 0xD9`). Tied on byte count. But `EXX` carries the alternate-set hazard documented in `_bmad-output/implementation-artifacts/8-4-exx-convention-reference.md` — using EXX inside a word that also calls into `bdos_putchar` (which itself does NOT use the alternate set) is fine, but using EXX inside a word that might be called from inside an EXX-using caller is a hazard. `PUSH BC / POP BC` has no such hazard surface.
3. **No follow-up-edit needed.** The interpret-mode tail is already intentionally primary-set (it operates directly on `IY+UserArea.*` slots and on HL/DE/BC for the loop). Switching to EXX would require either swapping the loop body to alternate registers (more invasive) or a four-EXX dance (`EXX` at entry, `EXX` before `bdos_putchar`, `EXX` after `bdos_putchar` returns, `EXX` at exit) — increases byte cost AND introduces a new EXX site to track in `8-4-exx-convention-reference.md`.

### Why the in-loop `PUSH BC / POP BC` envelopes are NOT redundant after the fix

Two distinct scopes:

- **In-loop PUSH BC / POP BC (lines 877/883 and 890/893):** save the LOOP COUNTER (C = remaining TIB chars to consume) across `bdos_putchar` (which clobbers BC) and across the `>IN` advance (which clobbers BC via the `IY+UserArea.tib_in` HL-build). These are correct as-is and continue to be load-bearing — the loop body continues to clobber and recover the COUNTER state of BC.
- **New function-level PUSH BC / POP BC (AC #2):** saves the ORIGINAL TOS (BC at function entry) across the entire interpret-mode work. The original TOS is restored AT EXIT, after the loop has finished and after the in-loop saves have all paired up.

Strictly nested scopes, one register pair. No conflict; both saves are necessary.

### Compile-mode vs interpret-mode threading reminder

`."` is IMMEDIATE. Two execution contexts, two completely different code paths inside `w_DOT_QUOTE_cf`:

1. **Compile state (state ≠ 0):** `."` runs at compile-time during the parse of a colon body. The compile-mode tail at `:816..832` calls `compile_string` (which parses the inline string from TIB and emits a `(S")` runtime call followed by the inline string into the dictionary), then emits `TYPE`'s xt as the next compiled cell. At RUN-TIME of the colon body, the compiled-out form executes: `(S")` pushes c-addr and sets BC = u; `TYPE` pops u (BC) and c-addr (data stack), prints, and pops the next cell as the new BC. Net stack effect of the compiled-out form: ( -- ). Correct.
2. **Interpret state (state == 0):** `."` runs at the REPL or at top level of an INCLUDED / EVALUATEd source. The interpret-mode tail at `:834..900` parses the inline string from TIB on-the-fly and prints each character via `bdos_putchar`. No (S") emission, no TYPE. The loop COUNTER lives in C; the original BC (= TOS at function entry) is destroyed unless saved/restored. Pre-Story-13.5.3: not saved. Post-Story-13.5.3: saved via the new outer envelope.

The split-mode design is the right factoring (compile mode uses the dictionary-emission path that's optimal at run-time; interpret mode uses the inline-print path that's optimal at one-shot REPL invocation). The bug is purely the missing TOS-preservation envelope in the interpret-mode tail — the design itself is sound.
