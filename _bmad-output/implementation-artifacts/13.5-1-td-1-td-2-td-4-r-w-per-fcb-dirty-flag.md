## Story

As an antforth user opening files in R/W mode for mixed read+write workflows,
I want `FILE-POSITION` to report the correct byte cursor mid-read, `REPOSITION-FILE` to commit pending partial-record writes safely instead of silently discarding them, and the W/O auto-flush path to be probe-covered,
So that mixed read+write FIDs return correct cursor information and survive a reposition without dropping bytes, and the W/O write-then-reposition workflow has matching test coverage so future regressions are caught.

This is the second story in Epic 13.5 (Phase-2 Cleanup Slate) — the process-recovery vehicle that gates `antforth 2.0`. It has zero new feature scope; every AC discharges debt named in the Epic 13 retro's Tag-Blocking Slate. Three tag-blockers close in this single dev-pass: TD-1 (FILE-POSITION accuracy), TD-2 (REPOSITION-FILE auto-flush), TD-4 (W/O probe coverage). The fix shape was pre-scoped at Story 13.3 Task 11 (the canonical forward-pointer); this story lands the deferred shape and keeps the bytes-per-fix discipline tight.

## Acceptance Criteria

1. **Given** the per-FCB "has-written" parallel array `fcb_has_written` from Story 13.5 (`src/file_access.asm:136`) which is the precedent for this story's parallel-array layout,
   **when** the new `fcb_dirty` per-FCB byte array is added to `src/file_access.asm`,
   **then** it lands as `fcb_dirty: DS FCB_POOL_COUNT` immediately after `fcb_has_written` at the data-region tail (target site `src/file_access.asm:136..137`; the post-edit line number for `fcb_dirty` is dev-pass-determined as edits to surrounding comments may shift the surface). Encoding: 0 = clean (DMA holds no uncommitted bytes — read-loaded, freshly-flushed, or freshly-acquired); non-zero = dirty (DMA holds at-least-one uncommitted byte from a `file_byte_write` that has not yet been committed via `bdos_write_seq`). The encoding mirrors `fcb_has_written` exactly so future readers can pattern-match the two arrays' shapes.

2. **Given** `pool_init` (`src/file_access.asm:144`) which initialises every parallel array at cold start, including the existing `fcb_has_written` zero-loop at `src/file_access.asm:196..202` (the `.pi_hw_loop` pattern),
   **when** Story 13.5.1 lands,
   **then** `pool_init` is extended with a parallel zero-loop for `fcb_dirty` immediately after the `.pi_hw_loop` block. The new loop is named `.pi_dirty_loop` (or equivalent — pick something that matches the existing `.pi_*_loop` family). Estimated cost: ~10 bytes (mirror of `.pi_hw_loop`). The loop is structurally identical to the has-written loop except for the array base address.

3. **Given** `pool_acquire` (`src/file_access.asm:212`) which clears `fcb_has_written[B]` at the `.pa_found` site (`src/file_access.asm:240..251`),
   **when** Story 13.5.1 lands,
   **then** `pool_acquire` also clears `fcb_dirty[B]` at the same `.pa_found` site (a fresh FCB starts both never-written AND clean — the two are conjunctively true at acquire time). The clear lands inside the existing `PUSH HL / PUSH BC / ... / POP BC / POP HL` envelope (so caller still sees HL = FCB ptr at exit). Estimated cost: ~6 bytes (a second `LD (HL), 0` after re-deriving the array base). Implementation pick: re-use the index→address compute pattern already in place; do NOT collapse the two stores into a single LDI/LDIR (the bytes aren't contiguous — `fcb_has_written` and `fcb_dirty` are adjacent but the parallel-array idiom keeps them as separate addressable arrays for clarity).

4. **Given** `pool_release` (`src/file_access.asm:266`) which resets `fcb_has_written[index]` at `src/file_access.asm:321..328` for stale-FID hardening (mirror of the `fcb_fam` reset at line 313..320),
   **when** Story 13.5.1 lands,
   **then** `pool_release` also resets `fcb_dirty[index]` to 0 at the same site. Mirrors the existing fcb_fam / fcb_has_written reset blocks. **Constraint:** the existing DE recovery from `.pr_save_h` / `.pr_save_l` immediately after the parallel-array resets (`src/file_access.asm:341..344`) must remain untouched — that is the Story 13.5 finding F1 fix and adding another array reset BEFORE it must not bypass the recovery. The new reset block lands BEFORE the `LD A, (.pr_save_h)` recovery line. Estimated cost: ~10 bytes (parallel to the `fcb_has_written` reset block at lines 321..328).

5. **Given** `file_byte_write` (`src/file_access.asm:709`) which currently sets `fcb_has_written[index] := 1` at function entry (`src/file_access.asm:717..728`) before any byte-write,
   **when** Story 13.5.1 lands,
   **then** `file_byte_write` ALSO sets `fcb_dirty[index] := 1` at the same site (post-byte-commit — the bit becomes correct AFTER the byte lands in DMA, but in practice setting at entry is structurally equivalent because `file_byte_write` either succeeds and DMA is dirty, or fails and DMA is undefined; the bit-set at entry covers the success path correctly and the failure path is dominated by other error handling). The set lands inside the existing index→address envelope. **Critical:** the set point is `file_byte_write` ENTRY, NOT a downstream site — `bdos_write_seq` is the wrong place to set dirty (bdos_write_seq COMMITS dirty to disk, so it CLEARS dirty on success, not sets it). Estimated cost: ~8 bytes (a second `LD (HL), 1` after re-deriving the array base — same shape as the has-written set already there).

6. **Given** `file_byte_read` (`src/file_access.asm:623`) which refills DMA via `F_READ_SEQ` at the `pos == 128` (or `pos > 128` post-Story-13.3 REPOSITION-encoded sentinel) refill arm (`src/file_access.asm:638..666`),
   **when** Story 13.5.1 lands,
   **then** `file_byte_read` clears `fcb_dirty[index] := 0` immediately after the post-`bdos_read_seq` success path (specifically: after the `OR A; JR NZ, .fbr_eof` check at `src/file_access.asm:648..649`, BEFORE the `pos := old_pos - 128` recompute at line 659..666). Rationale: a successful refill replaces DMA contents with read-mode bytes; whatever uncommitted writes were in DMA before the refill are no longer present. **Implementation note:** if the previous DMA was actually dirty (a real R/W mid-stream-mid-record case where a partial write was overwritten by a refill without flushing) that's a separate latent — but the current canonical Story-13.3 (t13) probe path lands a write, then closes, then reopens, then reads. The Story-13.4 INCLUDE family is R/O (no writes ever). The Story-13.5 audit-anchor is R/O (no writes). So the refill-clears-dirty case is the universal correct semantics for the existing call paths; any path that would WANT the dirty bit preserved across a refill is structurally wrong (it would mean "I wrote to DMA, didn't flush, then asked for new bytes" — silent data loss already). Estimated cost: ~12 bytes (index recovery + array address compute + zero store, lands inside the refill arm only — pos<128 fast path is unchanged). The existing `.fbr_idx` scratch already holds the index; reuse it.

7. **Given** `file_flush` (`src/file_access.asm:814`) which currently gates on `fcb_has_written[index] != 0` at `src/file_access.asm:835..847` (Story 13.5's structural fix),
   **when** Story 13.5.1 lands,
   **then** `file_flush` ALSO gates on `fcb_dirty[index] != 0`. The new gate lands AFTER the has-written gate and BEFORE the existing `pos == 0 → .ff_empty` short-circuit at line 853..855. Control flow:
   - has-written == 0 → `.ff_empty` (R/O / never-written R/W — Story 13.5 path, unchanged)
   - **NEW:** dirty == 0 → `.ff_empty` (R/W or W/O FCB that has ever-been-written but DMA currently holds no pending bytes — read-loaded after a refill, or freshly flushed)
   - pos == 0 → `.ff_empty` (existing post-record-boundary fast path)
   - pos >= 128 → `.ff_empty` (existing Story-13.2 R/O refill sentinel + Story-13.3 REPOSITION-encoded sentinel defence-in-depth)
   - else → fall through to pad + `bdos_write_seq` (the actual flush)
   
   On successful flush (the pad + bdos_write_seq path completes with A==0), `file_flush` MUST clear `fcb_dirty[index] := 0` at `.ff_empty`-return-equivalent. Rationale: post-flush DMA contents are committed to disk; the dirty bit must reset so a subsequent close on the same FCB doesn't double-flush. Implementation site: in the success path between line 893 (pos reset to 0) and line 901 (POP DE / RET), add the dirty clear. **Constraint:** the `.ff_empty` early-return paths (where flush was skipped) must NOT clear dirty unconditionally — the early-return paths leave dirty as-is, because nothing committed to disk. The clear is paired with the pad+write success path only. Estimated cost: ~25 bytes (the new dirty gate at entry: ~12 bytes; the post-success clear: ~12 bytes).

8. **Given** `bdos_write_seq` (`src/file_access.asm:516`) which sets `fcb_has_written[index] := 1` on A==0 success (`src/file_access.asm:523..547`),
   **when** Story 13.5.1 lands,
   **then** `bdos_write_seq` ALSO clears `fcb_dirty[index] := 0` on A==0 success at the same site. Rationale: every successful F_WRITE commits the current DMA to disk; the dirty bit must reset because DMA's contents are no longer "uncommitted bytes". The clear lands inside the existing `PUSH AF / PUSH BC / PUSH DE / fcb_idx_from_ptr / .bws_oor` envelope (the index→address compute is already there for has-written set; reuse it for the dirty clear in the same code block). **Critical:** has-written is SET (sticky), dirty is CLEARED — these are the OPPOSITE writes at the same call site. Both are correct: has-written says "this FCB has ever been written" (sticky 1); dirty says "DMA holds uncommitted bytes RIGHT NOW" (transient — cleared on commit). Estimated cost: ~8 bytes (a second store at the same address-compute site).

9. **Given** `w_FILE_POSITION_cf` (`src/file_access.asm:1876`) which currently has the buffer-loaded-decrement formula at `src/file_access.asm:1944..1956` (`if pos<128 AND fam_masked == 0` → decrement record_count_seq by 1) and the documented R/W mid-read accuracy gap at `src/file_access.asm:1867..1872`,
   **when** Story 13.5.1 lands,
   **then** the formula is extended to use the dirty bit instead of the fam_masked check. New rule: decrement record_count_seq by 1 when `pos<128 AND dirty==0` (DMA currently holds read data — the F_READ_SEQ that filled it auto-advanced CR by 1 past the loaded record). The R/O formula (currently `pos<128 AND fam_masked==0`) is replaced by the dirty formula (universal across all FAM modes). Verification table:
   
   | FAM | State | dirty | pos | Old formula | New formula | Correct |
   |-----|-------|-------|-----|-------------|-------------|---------|
   | R/O | post-OPEN, no read yet | 0 | 128 | no decrement | no decrement (pos>=128) | 0 — yes |
   | R/O | mid-read (read N bytes) | 0 | N<128 | decrement | decrement (dirty==0) | yes |
   | R/W | post-OPEN, no I/O yet | 0 | 0 | NO decrement (fam!=0) | NO decrement (pos==0)... | mismatch. See note. |
   | R/W | mid-write | 1 | N<128 | NO decrement (fam!=0) | NO decrement (dirty==1) | yes |
   | R/W | mid-read | 0 | N<128 | NO decrement (fam!=0) — **TD-1** | decrement (dirty==0) | yes |
   | W/O | post-OPEN | 0 | 0 | NO decrement (fam!=0) | NO decrement (pos==0)... | mismatch. See note. |
   | W/O | mid-write | 1 | N<128 | NO decrement (fam!=0) | NO decrement (dirty==1) | yes |
   
   **Note on the post-OPEN R/W and W/O cases (rows where the `fam!=0` Old formula and the dirty Old formula diverge):** in both cases pos==0 AND dirty==0 — so the new formula's decrement arm fires. But the old fast-path at `src/file_access.asm:1947..1949` skips the decrement when `L=0` (because `SUB 1` on L=0 leaves L=255 and CY=1, propagating the borrow into H and B; the resulting (L, H, B) value is wrong — wraps below zero). Verify the formula's behaviour on freshly-OPEN-W/O / freshly-OPEN-R/W FCBs. **Expected:** for a freshly-OPEN FCB, CR=0, EX=0, S2=0 → record_count_seq=0; pos==0; dirty==0. The dev-pass must add an explicit guard: do NOT decrement when record_count_seq is already 0 (i.e., when L==0 AND H==0 AND B==0). Or equivalently: only decrement when pos<128 AND dirty==0 AND record_count_seq > 0. Verify behaviour empirically with a probe; HALT if the formula needs broader surgery.

The existing `fac_bp+1` scratch slot used for `fam_masked` can be repurposed for `dirty` (no new scratch needed). Inline header comment at `src/file_access.asm:1867..1872` is updated to reflect the dirty-based formula and the post-Story-13.5.1 landing date. Estimated cost: ~12 bytes (formula tweak + guard).

### Why the dirty-flag (transient) ≠ has-written (sticky)

Both bits live as parallel byte arrays at the FCB pool tail. They look identical structurally. Their semantics differ:

| Bit | Encoding | Cleared at | Set at | Gates |
|-----|---|---|---|---|
| **has-written** (Story 13.5) | 0=never-written / non-zero=ever-written | pool_acquire / pool_release | bdos_write_seq A==0 success / file_byte_write entry | "should this FCB ever flush?" — closes R/O destructive flush wholesale |
| **dirty** (Story 13.5.1) | 0=clean (DMA holds no uncommitted bytes) / non-zero=dirty (DMA has uncommitted bytes) | pool_acquire / pool_release / file_byte_read refill / file_flush success / bdos_write_seq A==0 success | file_byte_write entry | "does DMA hold pending writes RIGHT NOW?" — closes R/W mid-read accuracy + R/W discard discipline + W/O reposition write loss |

**They coexist** — the file_flush dirty gate is conjunctive with the has-written gate. Both must be 1 (=true) for flush to fire. R/O case: has-written stays 0 → flush skipped (Story 13.5 path). R/W mid-read case: has-written=1 BUT dirty=0 → flush still skipped (Story 13.5.1 path). R/W mid-write case: has-written=1 AND dirty=1 → flush fires (correct).

The has-written bit set at `bdos_write_seq` A==0 stays sticky (set forever after first write) — that's the correct semantic for "this FCB has ever been written to disk". The dirty bit at the same site is CLEARED on success (the write committed; DMA is no longer dirty). Same call site, opposite writes.

### Why FILE-POSITION's decrement formula extension is single-line + guard

The current formula at line 1944..1956 has:
```
LD A, (fac_bp + 1)   ; A = fam_masked
OR A
JR NZ, .fp_no_dec
```

The fam_masked check is a single byte load + OR + branch. Replacing the load source from `fcb_fam` to `fcb_dirty` is mechanical (the fac_bp+1 scratch slot is reused; fetching dirty into it instead of fam_masked is one line earlier in the body — at line ~1898..1900, replace the `LD HL, BC; LD DE, fcb_fam; ADD HL, DE; LD A, (HL); AND 3; LD (fac_bp+1), A` with `LD HL, BC; LD DE, fcb_dirty; ADD HL, DE; LD A, (HL); LD (fac_bp+1), A`).

The underflow guard is the new bit: when record_count_seq is already 0 AND the formula tries to decrement, the result is 0xFFFFFFFF instead of 0. The guard is:
```
LD A, L
OR H
OR B
JR Z, .fp_no_dec    ; record_count_seq==0 already → no decrement
```

That's ~6 bytes inserted between the dirty-check and the SUB 1 / borrow-propagation chain.

### Why REPOSITION-FILE auto-flush is structurally safe NOW (vs Story 13.3's retraction)

The Story 13.3 (t13)-probe corruption fired because file_flush wrote stale read DMA back to disk at the read-walk-advanced FCB.CR. The mechanism:

1. R/W FCB, OPEN-FILE → CR=0, dirty=0, has-written=0
2. WRITE 5 bytes → DMA[0..4] = bytes, pos=5, dirty=1, has-written=1
3. (auto-flush would have fired here in Story 13.3's pick (i); deferred to REPOSITION)
4. REPOSITION-FILE to byte 0 → calls file_flush
5. **Pre-13.5.1 (Story 13.3 pick (ii) discard):** file_flush runs unconditionally, pads DMA[5..127] with 0x1A, F_WRITE_SEQ at CR=0 → writes "AAAAA" + 123×0x1A at record 0. CR advances to 1. Then REPOSITION sets R0..R2/CR/EX/S2 to 0. Then READ refills DMA[0..127] from record 0 (correct). All good.
6. (continue) READ 3 bytes → DMA[0..2] read into user buffer. dirty=0 (cleared on refill).
7. REPOSITION-FILE to byte 5 → calls file_flush. Pre-13.5.1: file_flush runs again (has-written=1). Pads DMA[3..127] with 0x1A, F_WRITE_SEQ at the post-read CR=1. This OVERWRITES record 1 with garbage — the (t13) corruption.

**Post-13.5.1:** at step 7, dirty=0 (cleared at step 6's READ refill). file_flush hits the new dirty gate and skips. No write at CR=1. REPOSITION proceeds correctly. Auto-flush is structurally safe.

The pre-13.5.1 Story-13.3 "discard discipline" was a band-aid: it skipped file_flush altogether at REPOSITION-FILE, preventing the corruption but also silently losing any pending partial write at step 4. The dirty-flag is the structural fix that allows the flush to fire only when there's real work to commit.

### CP/M 2.2 record-position semantics reminder (unchanged from Story 13.5)

The 36-byte FCB layout (`src/file_access.asm:75..86`) tracks record position via:
- **FCB.CR (offset 32)** — current record (sequential cursor; 0..127 within current extent)
- **FCB.EX (offset 12)** — current extent (low byte)
- **FCB.S2 (offset 14)** — extent high byte (BDOS-internal but meaningful for sequential walk past extent boundary)

`F_READ_SEQ` advances FCB.CR; on extent-boundary it advances FCB.EX (and possibly FCB.S2 via BDOS-internal logic). `F_WRITE_SEQ` writes at the FCB.CR-indexed record-position within the current extent and advances FCB.CR.

The Story-13.3 sentinel encoding (`pos = 128 + B` after REPOSITION-FILE; consumed by `file_byte_read`/`file_byte_write` to skip into the freshly-loaded record at offset B) interacts with the new dirty gate as follows: REPOSITION-FILE's auto-flush call lands BEFORE the sentinel is encoded into pos. So the flush operates on the pre-REPOSITION pos value (which is in 0..127 if dirty, or 128 if at refill sentinel). No interaction; the orderings are independent.

### Register-convention pick
