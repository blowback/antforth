## Challenges

### 1. iz-cpm-vs-hardware verdict-shape divergence (lesson candidate 15-B)

Story 15.5 run-1 hardware transcript revealed two iz-cpm sanity-pass false-positives:

- **Probe-design defect:** Bare-REPL `IF/ELSE/THEN` raised THROW −14 (compile-only word) on real hardware. iz-cpm's Makefile grep matched the literal verdict-token strings (`T6V=NO_LIMIT` / `T7V=NO_LIMIT`) in the *echoed source line* of `S" T6V=NO_LIMIT" TYPE`, not in actual probe output — false-positive SKIP. Fix: wrap verdict logic in `: VERDICT ... ;` colon def + numeric codes.
- **CR-1 M1 false-positive:** CR proposed adding a `DROP` before `LEAVE` in `TRY-FILL`'s failure path. iz-cpm sanity-passed the modified probe because iz-cpm never reaches the failure path (no exhaustion). Hardware run-3 surfaced `error -4: stack underflow` on the failure path — the original probe was correct, the proposed fix introduced the bug. Reverted.

**Pattern:** hardware-only code paths (failure paths under resource exhaustion; bare-REPL state-context boundaries; transcript grep-match scope) cannot be validated by iz-cpm sanity-pass alone. iz-cpm + grep is necessary but not sufficient.

### 2. TIB-128 line-length is a probe-authoring constraint (lesson candidate 15-C)

CR-1 H2 fix added a `CIM` close-ior fold to Probe 3's `TRY-CREATE` colon-def, pushing the line to 134 chars — over antforth's TIB-128 limit. Hardware paste truncated at char 128, mid-`NFILES` token; cascading `error -13: undefined word`. Resolved by splitting `TRY-CREATE` across two source lines at the `THEN`-boundary (legal inside compile state). **Probe colon-defs that touch verdict-fold logic should respect the 128-char source-line limit explicitly, not implicitly.**

### 3. Three hardware runs to land a 6-AC story

15.5 needed run-1 (probe-design defect surfaced), run-2 (B.9 + B.7 evaluation cleanly), run-3 (CR-1 H2 fix verification + M1 false-positive reversal). The cost of "hardware-real" verification is non-trivial. This is fine — the alternative (skipping or relying on iz-cpm) was a worse cost (the run-1 defect would not have surfaced) — but it's a calibration data point for future hardware-typed probe planning.

### 4. Sprint-status pre-state drift, again, in 15.1 and 15.5

Both 15.1 and 15.5 caught at /CR with the same Lesson 14-D class: dev-pass narration claimed canonical `ready-for-dev → in-progress → review`; actual on-disk transition was `backlog → review` (15.1 had the additional twist of an uncommitted retro-session rename). The lint we built across Epic 14 still cannot catch its own drafter's example. Status quo per Epic 14 retro Lesson 14-D — flagged, not new apparatus, consistent with Lesson 14-F.

### 5. CR-1 sub-agent runtime produced one false-positive (M1 in 15.5)

The /CR sub-agent finding in 15.5 M1 was a real adversarial-review reading — but the correction it proposed introduced the bug it claimed to fix. The fresh-context sub-agent did not have the runtime knowledge that `WRITE-FILE` leaves only one cell on the stack; its model of the probe's stack effect was wrong. Reverted via hardware run-3. **Pattern (lesson candidate 15-B sub-clause):** /CR adversarial review's structural-shape findings are high-value; its proposed fixes can introduce new defects when the fix touches code paths that only execute on hardware. Treat /CR proposed fixes as hypotheses to verify, not as ready-to-merge edits — especially when the proposed fix touches a hardware-only code path.
